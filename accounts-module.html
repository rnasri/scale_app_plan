Section A — Overview & Scope

This document is the single authoritative reference for the AIWS Accounts Foundation build — the organisation's centralised financial transaction engine: Chart of Accounts, General Ledger, AR/AP, Bank Reconciliation, GST, Audit Trail, Journal Entries, TDS/TCS, Multi-currency, Fixed Assets, Depreciation, Petty Cash, Cost Centre Accounting, E-Invoicing, and MIS Reports (prefix AC). It covers the 15 features from the Excel Accounts tab plus 1 feature identified in the client's Accounts Management Module PRD (AC-16). Together these 16 features define the scope of the scale_accounts custom app for Wave 1 (Aug 1 – Sep 5, 2026) — the first app built, since every other Finance-side feature depends on it.

Companion document — Finance Analytics

Budgeting, forecasting, cash flow, working capital, profitability, and strategic finance (14 more features, prefix FI) are scoped separately in finance-module.html, under a dedicated scale_finance app that depends on this one. Both apps are led by Uday. Two features exist in both documents because the client's source material (Excel tabs and PDFs) independently lists them in both scopes — see the flagged callouts on AC-13 and AC-16 below for exactly how to handle each.

How to navigate to the Accounts module: Launch the bench → open your Scale site → click the Scale app launcher → find Scale Accounts in the left sidebar. This entry appears after T00 (app creation) and bench migrate.

App: scale_accounts (Python package name, git folder name, and ERPNext app name — all the same).  Platform: Frappe v15 + ERPNext v15 + India Compliance app (mandatory for GST / TDS / E-Invoicing).

Module Vision (from the client PRD): "The Accounts Management Module is designed to serve as the organization's centralized financial transaction engine. It provides complete control over accounting operations while ensuring compliance with statutory regulations, maintaining financial accuracy, and delivering real-time financial visibility... integrates with Sales, Purchase, Inventory, Manufacturing, HR, Banking, and Finance to provide a single source of truth for all financial transactions."

Primary Users (per PRD): Accountant · Senior Accountant · Accounts Manager · Finance Controller · CFO · Auditor · Tax Consultant · CEO · Business Owner.

Client PRD Analysis — 1 additional feature identified (Accounts Management Module PRD, Jul 2026)

The client Accounts Management Module PRD contains 15 numbered feature sections that map 1:1 to the Excel Accounts tab (same names, same order — verified). The PRD closes with an Executive Dashboard specification that is not in the original Excel scope.

  • AC-16 — Executive Dashboard (CFO & CXO View) — a consolidated real-time view of 15 KPIs: Cash & Bank Balance, Accounts Receivable, Accounts Payable, Daily Collections, Daily Payments, Revenue & Expenses, P&L Snapshot, GST Liability, TDS/TCS Status, Fixed Asset Value, Budget vs Actual, Cost Centre Performance, Pending Journal Approvals, Audit Exceptions, AI Financial Health Score, Top AI Recommendations.

All 15 Excel Accounts features (AC-01 to AC-15) are in Wave 1 scope. AC-16 is partially Wave 1 (T12 — the 13 KPIs sourced from this module) and partially Wave 2 (V06 — AI Financial Health Score, Top AI Recommendations). See the AC-16 accordion below for the overlap with Finance module's own FI-16.

⚠ Note to AI Team — on the PRD's AI Feature lists

The client PRD lists 4–8 "AI Features" under every one of the 15 sections (over 60 AI bullet points total — e.g. "recommend account mappings," "detect duplicate accounts," "predict payment delays," "forecast exchange rate exposure"). Building every single one as a Wave 1 task is out of scope and would stall the core bookkeeping build. This document triages them into four grouped Wave 2 AI tasks (V03–V06) that cover the same ground thematically — see the AI Track section. Do not modify any upstream Frappe/ERPNext/India Compliance source files; all custom logic lives exclusively inside apps/scale_accounts/. Hook paths must use the outer Python package name only — e.g. scale_accounts.msme_hooks.fn, never scale_accounts.scale_accounts.msme_hooks.fn.

C.2 — The Change-Test-Commit Cycle

  1. Make the change — in ERPNext UI or in a Python file.
  2. Test on your bench — submit a test transaction, verify the behaviour.
  3. Export fixtures (UI-made changes only): bench --site <site> export-fixtures --app scale_accounts
  4. Commit: git add apps/scale_accounts/ → git commit -m "feat(accounts): <description>"
  5. Push: git push origin main
  6. Notify team: after pull, run bench --site <site> migrate to load DocType changes.

C.3 — How to Add a Custom Field (example: Bank Transaction duplicate flag)

  1. Go to: ERPNext → Customize Form → DocType = Bank Transaction
  2. Click Add Row. Field Label: Possible Duplicate · Field Name: scale_accounts_dup_flag · Type: Check · Module: Scale Accounts
  3. Save. Run: bench --site <site> export-fixtures --app scale_accounts
  4. Commit the fixtures/custom_field.json file.

C.4 — How to Write a Python Hook (Journal Entry period lock)

# apps/scale_accounts/scale_accounts/journal_hooks.py

import frappe
from frappe.utils import getdate

def check_period_lock(doc, method=None):
    """Block Journal Entry submission if posting_date falls in a frozen accounting period."""
    frozen_until = frappe.db.get_single_value("Accounts Settings", "acc_frozen_upto")
    if frozen_until and getdate(doc.posting_date) <= getdate(frozen_until):
        frappe.throw(
            f"Journal Entry posting date {doc.posting_date} falls within a frozen "
            f"accounting period (frozen up to {frozen_until}). Contact Finance Controller."
        )

Declare in hooks.py: "Journal Entry": {"before_submit": "scale_accounts.journal_hooks.check_period_lock"}. After saving hooks.py, run bench restart — no migrate needed.

Accounts Foundation — Feature Breakdown

Expand each feature to see what exists natively in ERPNext, what needs to be configured, and the lean implementation approach.

Group 1 — Core Bookkeeping (AC-01 to AC-04)

OOTB AC-01 · Chart of Accounts ▶

What already works: ERPNext auto-generates a Chart of Accounts tree the moment a Company is created — root groups Assets, Liabilities, Equity, Revenue, Direct Expenses, Indirect Expenses, Cost of Goods Sold, and Other Income are created automatically with the India standard template. Each account carries Account Code, Account Name, Parent Account, Account Type, Currency, and Status natively.

Client PRD requirement: Support Company-wise CoA, Branch-wise CoA, Import/Export CoA, Account Merge, Account Freeze, Cost Centre Mapping per account, and Tax Mapping per account.

What to configure:

  • Select the India CoA template during Company creation — never start from a blank CoA
  • Add/rename child accounts under each root group to match the client's actual ledger structure (specific bank accounts, product revenue heads, department expense heads)
  • Create GST liability accounts: CGST Payable, SGST Payable, IGST Payable — under Indirect Taxes sub-group
  • Create TDS Payable accounts per Section (194C, 194J, 192B etc.) under Current Liabilities
  • Map all legacy account codes from the client's previous accounting software — critical before any transaction posting
  • Account Merge: use ERPNext's native "Merge Account" action (right-click account in tree) if legacy CoA has duplicate/near-duplicate accounts
  • Account Freeze: set "Freeze Account" = Yes on any account that should stop accepting new entries (e.g. a closed bank account)
  • Pre-work: Get the client's existing trial balance from their current software before starting — this blocks the whole task.
Delay Risk — High: mapping legacy CoA to the standard tree and configuring tax accounts is the single biggest source of go-live delay. Do not let this task slip past Aug 2.
OOTB AC-02 · General Ledger Management ▶

What already works: Fully automatic — every transaction submitted in ERPNext (Sales, Purchase, Inventory, Payroll, Banking, Manufacturing, Assets, Expense Claims) posts a General Ledger entry the moment it's submitted, drillable back to its source document. Manual Ledger Posting via Journal Entry covers Journal Adjustments, Opening Entries, Closing Entries, and Reversals. No separate configuration is needed once the Chart of Accounts (AC-01) is mapped correctly — this feature is a consequence of AC-01, not an independent build.

Client PRD requirement: Auto-generate ledger entries from Sales, Purchase, Inventory, Payroll, Banking, Manufacturing, Assets, Expense Claims. Support Manual Ledger Posting, Journal Adjustments, Opening Entries, Closing Entries, Reversals. Each ledger entry should include: Voucher Number, Date, Account, Debit, Credit, Cost Centre, Project, Branch, Narration, User, Reference Document.

What to verify (no build needed):

  • Confirm every native GL Entry row already carries all 11 PRD-required fields — Frappe's GL Entry DocType has Voucher No, Posting Date, Account, Debit, Credit, Cost Center, Project, and a reference back to the source Voucher Type/Voucher No natively; Branch and Narration are also native fields on the source documents. Nothing to add.
  • Go to top search bar → type General Ledger → run it after T01's test transactions → confirm every column the PRD asks for is visible and filterable.
  • Reversals: use ERPNext's native "Cancel" + auto-generated reversing Journal Entry, or a manual reversal Journal Entry template (see AC-07)

AI Features requested in the PRD for this section (detect duplicate ledger postings, identify abnormal transactions, recommend correcting entries, highlight posting inconsistencies, predict month-end closing issues) and its Reports (General Ledger, Ledger Summary, Ledger Audit, Transaction Register) are covered by the native General Ledger report plus the Duplicate & Anomaly Detection Suite (Wave 2, V03) below — see that accordion for the AI build.

OOTB AC-03 · Accounts Receivable & Accounts Payable ▶

What already works: Fully native. Every Sales Invoice creates an AR entry; every Purchase Invoice creates an AP entry. Payment Entry reconciles against invoices automatically. Aging buckets (0–30, 31–60, 61–90, 90+ days) are built in. Customer & Vendor statements are native, drillable to source.

Client PRD requirement: AR tracks Customer Invoices, Credit Notes, Receipts, Outstanding Amount, Ageing, Payment History, Credit Limit. AP tracks Vendor Bills, Debit Notes, Payments, Outstanding, Due Dates, Credit Terms. Both need Ageing Analysis, Payment Schedule, Collection Calendar, and Customer & Vendor Statements.

What to configure:

  • Define Payment Terms: Net 30, Net 45, Net 60, 50% Advance + 50% on Delivery — create templates in ERPNext UI
  • Set Credit Limits per Customer (Customer master → Credit Limit field)
  • Enable automatic credit hold: "Credit Controller" role + "Block Invoice on Credit Limit" in Company settings
  • Configure dunning: Notification Rules on Sales Invoice for 7-day and 30-day overdue alerts
  • Enable Collection Letters via ERPNext's native Dunning DocType — this becomes the client's "Collection Calendar"
  • Set default Payment Terms on each Customer and Supplier master to avoid manual selection on every invoice
OOTB AC-04 · Bank Reconciliation ▶

What already works: Native Bank Reconciliation Tool accepts bank statement CSV upload and auto-matches transactions by amount and date. Unmatched entries are flagged for manual review only — humans see exceptions, not every line.

Client PRD requirement: Support multiple Bank Accounts, Bank Statement Import, Automatic Matching, Manual Matching, Unmatched Transaction Review, Bank Charges, Interest Entries. Track Deposits, Withdrawals, Transfers, Returned Cheques, Bank Charges.

What to configure:

  • Create one Bank Account DocType per actual bank account (SBI Current, HDFC CC, etc.) — link each to its GL account in CoA
  • Test CSV column mapping against your bank's actual statement format — each bank exports different column names
  • Set up daily bank balance tracking: enable "Balance as per Bank Statement" field on Bank Account
  • Configure Bank Transaction auto-match rules in Payment Reconciliation settings
  • Map Bank Charges and Interest Entries to their own GL accounts so they post automatically during reconciliation
  • Known issue: HDFC and Axis bank statement CSVs use non-standard date formats — you may need a one-time pre-processing script to normalise dates before upload. Test with the first actual statement.

Group 2 — Tax Compliance (AC-05, AC-08, AC-14)

App Install AC-05 · Tax Compliance (GST) ▶

What exists natively (without India Compliance): Generic tax percentage on Sales Taxes and Charges Template. No GSTIN validation, no HSN codes, no GSTR reports. India Compliance app is mandatory — verified Frappe-approved app.

Client PRD requirement: Manage GST Registration, GST Rates, HSN/SAC Codes, Input Tax Credit (ITC), Output GST, Reverse Charge, Place of Supply. Support GSTR-1, GSTR-3B, GSTR-9, GST Reconciliation, E-Way Bill Integration.

What to install and configure:

  • Install India Compliance app: bench get-app india_compliance → bench --site <site> install-app india_compliance
  • Register GST credentials in India Compliance Settings (GSTIN, API username, state code)
  • Create Item Tax Templates per GST rate: 0%, 5%, 12%, 18%, 28% — map CGST + SGST + IGST split correctly
  • Add HSN/SAC codes to every Item master — mandatory for GSTR-1 filing
  • Validate GSTIN on each Customer and Supplier master via the built-in GSTIN lookup
  • Test GSTR-1 export: create 3 sample invoices → run GSTR-1 report → verify B2B, B2C, HSN summary sections
  • Configure GSTR-3B monthly and GSTR-9 annual payment schedule via Notification
  • Enable GST Reconciliation: India Compliance auto-fetches GSTR-2B and compares against Purchase Invoices
Delay Risk — High: HSN code mapping requires the complete Item master list from the client. Missing or wrong HSN codes cause GSTR-1 rejection.
OOTB AC-08 · TDS / TCS Management ▶

What already works: Tax Withholding Category DocType supports TDS deduction by rate and annual threshold. System auto-appends TDS row on Purchase Invoice submission. TDS Certificate generation (Form 16A) native. TCS on Sales Invoice also supported.

Client PRD requirement: Manage TDS Categories, Deductor Details, Deductee Details, PAN Validation, Challans, Certificates (Form 16A/27D), Quarterly Returns. Support Auto Deduction, Threshold Validation, Vendor TDS, Customer TCS, Interest & Penalty Calculation.

What to configure:

  • Create Tax Withholding Categories for current FY: 194C (contractors, 1%/2%), 194J (professional fees, 10%), 192B (salary TDS — handled via payroll), 194H (commission, 5%), 194I (rent, 10%/2%), 194Q (purchase of goods, 0.1%)
  • Set annual thresholds per category (e.g. 194C threshold = ₹30,000 per transaction or ₹1,00,000 per year)
  • Link Tax Withholding Category to each Supplier master — system auto-applies on invoice creation
  • Validate PAN on Supplier master before linking — TDS rate doubles under Section 206AA if PAN is invalid/missing
  • Test: submit a test Purchase Invoice above the threshold → verify TDS deduction row appears automatically
  • Schedule quarterly TDS Return reminders via Notification (26Q deadline: 31st Jul / 31st Oct / 31st Jan / 31st May)

Reports (per PRD): TDS Register and TCS Register are native (Tax Withholding Details report, filtered by category). Challan Summary and Return Status are not native — add as a small Script Report on the Scale Accounts workspace that lists each quarter's challan payments and 26Q filing status, sourced from the Tax Withholding Category records already configured above.

App Install AC-14 · E-Invoicing & GST Filing ▶

What exists natively: Standard PDF invoice only. No IRN, no QR code, no E-Way Bill API integration. Requires India Compliance app (same app as AC-05 — install once, covers both).

Client PRD requirement: Support IRN Generation, QR Code Generation, E-Invoice Cancellation, E-Way Bill, GST Portal Integration, Return Preparation, Filing Status Tracking.

What to configure:

  • Enable E-Invoicing in India Compliance Settings → provide GSP API credentials (NIC portal username/password)
  • On Sales Invoice submit → IRN auto-generated + QR code embedded → E-Invoice PDF format auto-applied
  • Configure E-Way Bill: set transporter details template, vehicle type defaults, bulk generation for multi-item dispatches
  • Build E-Invoice Register and Filing Status Tracking dashboard as Script Reports/Number Cards on the Scale Accounts workspace
  • Test IRN generation on staging/sandbox NIC endpoint before going live — NIC provides a sandbox environment
  • Applicability check: E-Invoicing mandatory if turnover > ₹5 Cr. Confirm applicability threshold with Uday before implementing.

Reports (per PRD): E-Invoice Register and Filing Status Tracking are built above. IRN Summary (count of generated/cancelled IRNs per period) and the Filing Dashboard (consolidated GSTR + E-Invoice filing status) are small additions to the same Script Report — group them together rather than building four separate reports.

Group 3 — Journals, Controls, Multi-currency, Petty Cash (AC-06, AC-07, AC-09, AC-12)

OOTB AC-07 · Journal Entries ▶

What already works: Journal Entry DocType enforces balanced debit/credit only — cannot submit an unbalanced entry. Supports multi-currency, Cost Centre tagging, Project tagging. Templates for recurring entries. Approval via standard Workflow DocType.

Client PRD requirement: Support Standard, Recurring, Reversal, Opening, Closing, and Intercompany Journal Entry types. Approval Workflow: Accountant → Accounts Manager → Finance Controller.

What to configure:

  • Create Journal Entry Templates for routine entries: Monthly Depreciation, Prepaid Expense amortisation, Accrual entries, Provision entries, Opening/Closing entries
  • Set up approval Workflow on Journal Entry: Draft → Accountant Review → Accounts Manager → Finance Controller Approve → Submitted
  • Restrict Journal Entry creation to Finance Controller and above for amounts > ₹1 lakh (via User Permissions)
  • Enable period locking: set "Accounts Frozen Up To" date monthly after period close — the journal_hooks.check_period_lock hook (Section C.4) enforces this in code, not just UI
OOTB AC-06 · Audit Trail & AC-09 · Multi-Currency Accounting ▶

Audit Trail — what already works: Enable "Track Changes" in System Settings → applies globally to all DocTypes. Cannot be disabled once enabled (compliance-grade, by design). Creates a "Version" record for every field change with before/after values, user name, and timestamp — visible in the document's own timeline.

Client PRD requirement: Track Record Creation, Modification, Deletion, User Activity, Login History, Approval History, Document Versioning. Store User, Timestamp, IP Address, Previous Value, New Value.

What to configure:

  • Enable "Track Changes" in System Settings — this is a one-time, irreversible toggle; confirm with Uday before enabling
  • Login History is native — visible per User under Security → User Activity Log
  • IP Address capture: enabled by default in Frappe's Activity Log — no config needed

Multi-Currency — what already works: Native Exchange Revaluation posts both flavours of forex gain/loss the PRD asks for automatically: Realized Gain/Loss is posted the moment a foreign-currency invoice is paid at a different rate than it was booked at (via the Payment Entry itself); Unrealized Gain/Loss is posted at period-end by the Exchange Rate Revaluation tool, which marks-to-market any still-open foreign-currency AR/AP balances. Supports party-wise currencies — Customer Currency and Vendor Currency are both fields on the Customer/Supplier master, independent of the Company's own base currency, and multiple base currencies are supported for multi-company setups.

Client PRD requirement: Support Multiple Base Currencies, Customer Currency, Vendor Currency, Exchange Rate Tables, Realized Gain/Loss, Unrealized Gain/Loss, Currency Revaluation.

What to configure:

  • Create foreign currency accounts: USD Bank Account → linked to GL account "HDFC USD Account" under Bank sub-group
  • Set Default Currency on any Customer/Supplier master that transacts in a non-base currency — this is the "Customer Currency" / "Vendor Currency" requirement, native fields, no custom work needed
  • Enable Currency Exchange rate auto-fetching: System Settings → Currency Exchange → set RBI/Frankfurter API — this populates the native "Currency Exchange" list, which is the PRD's "Exchange Rate Tables" requirement
