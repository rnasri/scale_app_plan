Frappe Extension Guide:
How to Build Without Breaking

The correct way to extend ERPNext, Frappe CRM, and Frappe HR — using the Accounts & Finance module as a worked example across all customization levels.

Version 1.0 · July 2026 Pixaflip Technologies × SIL For internal developer distribution

1The Single Most Important Concept

You never copy or modify Frappe/ERPNext/CRM source code. You install your custom app alongside them on the same server. Both apps share the same database. Your app only contains the differences — the extensions and additions.

This is the question every new developer asks: "If I create a new app, how does it get all the existing Frappe features?" The answer is: it doesn't need to — because both apps are installed on the same server at the same time.

How apps coexist on a Frappe bench

What this means in practice

✗ What you might think you need to do

  • Copy ERPNext's accounts/ folder into your app
  • Fork the erpnext repo and edit payment_entry.py
  • Duplicate the Sales Invoice DocType definition
  • Maintain your own branch of ERPNext for AIWS

✓ What you actually do

  • Install both ERPNext and your app on the same bench
  • Add Custom Fields to ERPNext's DocTypes via fixtures
  • Hook into ERPNext's events via hooks.py
  • Override classes by inheriting from ERPNext's originals

The fork trap: Forking ERPNext to add a field means every future ERPNext upgrade becomes a painful manual merge. Within 6 months, you're running a version of ERPNext that nobody else uses, with no security patches and no community support. Custom apps eliminate this entirely.

2The 5 Extension Levels — Quick Reference

Every feature request maps to one of these levels. Always start from Level 0 and only escalate when that level runs out of capability.

Level Name Tools used When to use Upgrade risk
0 Configure Roles, Workflows, Notifications, Print Formats, Workspaces Feature works exactly as-is in ERPNext None
1 Custom Fields & Property Setters Custom Field fixture, Property Setter fixture Right DocType exists but needs extra fields Very low
2 Server & Client Scripts doc_events in hooks.py, Server Script, Client Script Needs business logic on existing DocType events Low
3 Custom DocType or Override Class New DocType JSON + Python controller, override_doctype_class New entity needed, or existing class behaviour must change Medium — test on every ERPNext upgrade
4 Custom Pages, APIs, Background Jobs Frappe UI pages, @frappe.whitelist(), scheduler events External portal, heavy async processing, third-party integration Medium

3Worked Examples — Accounts & Finance Module

The Accounts module is nearly 90% covered by ERPNext out-of-the-box. These 5 examples use realistic AIWS Finance requirements to show exactly what each extension level looks like in practice — from a two-line fixture to a full custom DocType with a scheduler.

Level 1 — Custom Fields
Example A: Budget Revision Tracking
Adding fields to ERPNext's existing Budget DocType — no code, no fork

Business requirement

Finance controllers need to track how many times a budget has been revised and who approved the final version. ERPNext's Budget DocType has none of these fields.

ERPNext provides

The Budget DocType with: Company, Cost Centre, Fiscal Year, Budget Against, and monthly amount rows. Solid foundation — but missing revision history.

What we build in scale_accounts

Two Custom Fields added to the existing Budget DocType, stored as fixture JSON in our app:

    "fieldname": "scale_revision_no",
    "fieldtype": "Int",
    "label": "Revision No.",
    "default": "0",
    "read_only": 1,
    "insert_after": "fiscal_year",
    "module": "AIWS Finance"
  },

    "fieldname": "scale_approved_by",

    "options": "User",

Result: ERPNext's Budget form now shows "Revision No." and "Approved By" as if they were always there. When ERPNext releases v17, bench update runs, and these fields survive untouched because they live in our app, not in ERPNext's source.

Level 2 — Server Script / Hook
Example B: Auto Gross Margin on Sales Invoice Submit
Hooking into ERPNext's Sales Invoice lifecycle to inject business logic

Business requirement

When a Sales Invoice is submitted, automatically compute the gross margin % (selling price − cost price / selling price) per line item and store it — for use in profitability reports without any manual entry.

ERPNext provides

The Sales Invoice DocType with Item rows containing rate (selling price) and valuation_rate (cost, from stock). No margin calculation exists.

Step 1 — Add the storage field (Level 1 first)

Custom Field on Sales Invoice Item
{
  "dt": "Sales Invoice Item",        ← child table of Sales Invoice
  "fieldname": "scale_gross_margin_pct",
  "fieldtype": "Percent",
  "label": "Gross Margin %",
  "read_only": 1,
  "in_list_view": 1
}

Step 2 — Hook into on_submit to compute it

scale_accounts/hooks.py
doc_events = {
    "Sales Invoice": {
        "on_submit": "scale_accounts.finance.sales_invoice.compute_margins"
    }
}
# Frappe calls our function automatically after every Sales Invoice submit.
# We did not touch ERPNext's sales_invoice.py at all.
scale_accounts/finance/sales_invoice.py
import frappe

def compute_margins(doc, method):
    """Called by Frappe after Sales Invoice is submitted."""
    updated = False
    for item in doc.items:
        if item.rate and item.valuation_rate:
            margin = ((item.rate - item.valuation_rate) / item.rate) * 100
            frappe.db.set_value(
                "Sales Invoice Item",
                item.name,
                "scale_gross_margin_pct",
                round(margin, 2)
            )
            updated = True
    if updated:
        frappe.db.commit()

Key insight: The function signature (doc, method) is Frappe's convention for hook callbacks. doc is the full Sales Invoice object — all its fields and child rows are available. We never imported anything from ERPNext. Frappe passed the document to us automatically.

Level 3 — Override Class
Example C: Payment Entry — TDS Auto-Deduction
Extending ERPNext's Payment Entry Python class by inheriting from it

Business requirement

When posting a vendor payment above ₹30,000, the system must automatically calculate TDS (Tax Deducted at Source) at the applicable rate, store the TDS amount, and block submission if the TDS entry hasn't been acknowledged.

Why not a Server Script?

A Server Script can add validation but cannot reliably modify ERPNext's own validate() logic mid-stream or access internal ERPNext helper methods needed for TDS calculations. We need to override the class itself.

Step 1 — Tell Frappe to use our class instead

scale_accounts/hooks.py
override_doctype_class = {
    "Payment Entry": "scale_accounts.overrides.payment_entry.ScalePaymentEntry"
}
# Frappe will instantiate OUR class whenever a Payment Entry is created/saved.
# ERPNext's original class still exists — we inherit from it.

Step 2 — Write the override, inheriting everything

scale_accounts/overrides/payment_entry.py
import frappe
from erpnext.accounts.doctype.payment_entry.payment_entry import PaymentEntry

class ScalePaymentEntry(PaymentEntry):
    """
    Extends ERPNext's PaymentEntry.
    All of ERPNext's logic is inherited — we only ADD to it.
    """

    def validate(self):
        super().validate()         # ← run ERPNext's full validate first
        self._scale_compute_tds()   # ← then add our logic

    def _scale_compute_tds(self):
        if self.payment_type != "Pay":
            return                     # only on outgoing payments

        tds_rate = self._get_tds_rate(self.party)
        if not tds_rate or self.paid_amount < 30000:
            return

        tds_amount = round(self.paid_amount * tds_rate / 100, 2)
        self.scale_tds_amount  = tds_amount
        self.scale_tds_rate_pct = tds_rate

        if not self.scale_tds_acknowledged:
            frappe.throw(
                f"TDS of ₹{tds_amount:,.2f} ({tds_rate}%) applies to this payment. "
                "Check 'TDS Acknowledged' to proceed."
            )

    def _get_tds_rate(self, supplier):
        return frappe.db.get_value(
            "Supplier", supplier, "scale_tds_rate"
        ) or 0

The super().validate() line is critical. It runs ERPNext's full, complex Payment Entry validation — currency checks, account type checks, GL impact previews. We get all of that for free. Our 20 lines of code sit on top of hundreds of lines of ERPNext logic we never had to write.

Level 3 — New Custom DocType
Example D: MSME Compliance Tracker
Building a brand-new entity that links to ERPNext's Supplier — no equivalent exists in ERPNext

Business requirement

Indian MSME regulations require payments to MSME vendors within 45 days of invoice date. The Finance team needs a tracker that: records MSME registrations, monitors outstanding invoices, flags breaches, and generates a compliance report.

ERPNext provides

Supplier DocType (name, GSTIN, payment terms). Accounts Payable aging report. No MSME-specific tracking whatsoever. This is a full Level 3 build.

Python controller with scheduler

scale_accounts/doctype/scale_msme_tracker/scale_msme_tracker.py
import frappe
from frappe.model.document import Document
from frappe.utils import today, date_diff

class AiwsMsmeTracker(Document):

    def validate(self):
        if not self.udyam_number:
            frappe.throw("Udyam Registration Number is required for MSME tracking.")

    def on_submit(self):
        # Mark supplier as MSME in Supplier master
        frappe.db.set_value("Supplier", self.supplier, "scale_is_msme", 1)
        frappe.db.set_value("Supplier", self.supplier, "scale_msme_tracker", self.name)


# ── Scheduled job — runs daily ──────────────────────────────

def check_msme_breaches():
    """Called by Frappe scheduler daily. Flags near-breach MSME invoices."""
    trackers = frappe.get_all("AIWS MSME Tracker", filters={"docstatus": 1})

    for t in trackers:
        doc = frappe.get_doc("AIWS MSME Tracker", t.name)
        # pull outstanding purchase invoices for this supplier
        invoices = frappe.db.sql("""
            SELECT name, posting_date, outstanding_amount
            FROM   `tabPurchase Invoice`
            WHERE  supplier = %(sup)s
            AND    docstatus = 1
            AND    outstanding_amount > 0
        """, {"sup": doc.supplier}, as_dict=True)

        for inv in invoices:
            days_elapsed = date_diff(today(), inv.posting_date)
            days_left    = doc.payment_due_days - days_elapsed
            if days_left <= 7:     # alert when 7 or fewer days remain
                frappe.sendmail(
                    recipients=[frappe.db.get_single_value("AIWS Finance Settings", "finance_controller_email")],
                    subject=f"MSME Alert: {inv.name} due in {days_left} days",
                    message=f"Supplier: {doc.supplier} | Amount: ₹{inv.outstanding_amount:,.0f}"
                )
scale_accounts/hooks.py — register the daily job
scheduler_events = {
    "daily": ["scale_accounts.doctype.scale_msme_tracker.scale_msme_tracker.check_msme_breaches"]
}
Level 4 — Script Report
Example E: Working Capital Report
A custom analytical report reading ERPNext's GL Entries and Balance Sheet data

Business requirement

The Finance Controller needs a monthly working capital analysis: Current Assets, Current Liabilities, Net Working Capital, and Days Payable Outstanding — with a 12-month trend. ERPNext has a Balance Sheet but no working capital calculation.

ERPNext provides

GL Entry table (tabGL Entry), Account master with account_type and root_type. All the raw data — we just need to query it intelligently.

scale_accounts/report/scale_working_capital/scale_working_capital.py
import frappe
from frappe.utils import getdate, add_months

def execute(filters=None):
    columns = _get_columns()
    data    = _get_data(filters)
    return columns, data

def _get_columns():
    return [
        {"label": "Period",               "fieldtype": "Data",     "width": 120},
        {"label": "Current Assets (₹)",     "fieldtype": "Currency", "width": 160},
        {"label": "Current Liabilities (₹)", "fieldtype": "Currency", "width": 160},
        {"label": "Net Working Capital (₹)", "fieldtype": "Currency", "width": 160},
        {"label": "DPO (days)",              "fieldtype": "Int",      "width": 100},
    ]

def _get_data(filters):
    company  = filters.get("company")
    end_date = getdate(filters.get("to_date"))
    rows = []

    for i in range(12):                      # 12-month trend
        period_end   = add_months(end_date, -i)
        period_label = period_end.strftime("%b %Y")

        current_assets = _get_balance(company, "Asset",     "Current Asset",     period_end)
        current_liab   = _get_balance(company, "Liability", "Current Liability", period_end)
        net_wc         = current_assets - current_liab
        dpo            = _get_dpo(company, period_end)

        rows.append([period_label, current_assets, current_liab, net_wc, dpo])

    return rows

def _get_balance(company, root_type, account_type, as_of_date):
    # Query GL Entry — ERPNext's core accounting table
    result = frappe.db.sql("""
        SELECT COALESCE(SUM(gle.debit - gle.credit), 0) AS balance
        FROM   `tabGL Entry` gle
        JOIN   `tabAccount` acc ON acc.name = gle.account
        WHERE  gle.company     = %(company)s
        AND    acc.root_type   = %(root_type)s
        AND    acc.account_type = %(account_type)s
        AND    gle.posting_date <= %(as_of_date)s
        AND    gle.is_cancelled = 0
    """, {
        "company": company, "root_type": root_type,
        "account_type": account_type, "as_of_date": as_of_date
    })
    return abs(result[0][0]) if result else 0

We read ERPNext's tables directly (tabGL Entry, tabAccount) but write nothing to them. This is the safe pattern for Script Reports — read from ERPNext's data, produce your own analytical output. The report appears in Frappe's standard report list and is accessible to the right roles.

4Anti-Patterns — What NOT to Do

Never do these

  • Edit any file inside apps/frappe/, apps/erpnext/, apps/crm/, or apps/hrms/
  • Run git commit inside an ERPNext/Frappe app directory
  • Write raw UPDATE SQL directly against ERP tables — use frappe.db.set_value() or doc.save()
  • Import between two AIWS apps: from scale_sales import ... inside scale_accounts
  • Use frappe.flags.ignore_permissions = True without a documented reason in a comment above it
  • Store API keys, passwords, or tokens in Python source files — use a Password field on a Settings DocType
  • Skip writing tests because "it's just a small script"
  • Make manual config changes on a live site without also adding them to fixtures in your app

The upgrade contract

Before any ERPNext or Frappe version upgrade:

  1. 1
    Clone production to a test benchNever test upgrades on production
  2. 2
    Run bench update on the cloneCheck for migration errors
  3. 3
    Run the full AIWS test suitebench run-tests --app scale_accounts
  4. 4
    Specifically test all override classesThese are most likely to break if ERPNext's internal method signatures change
  5. 5
    Fix any breakages in your app — never in ERPNextIf ERPNext's API changed, update your override to match the new signature

5Decision Reference — Which Level for This Feature?

Ask yourselfAnswerLevel to use
Does ERPNext handle this exactly, with no changes? Yes Level 0 — configure roles/workflows/print formats. Export as fixtures.
Does the right DocType exist, but it's missing 1–5 fields? Yes Level 1 — Custom Fields in fixture JSON. Use scale_ prefix on all fieldnames.
Do I need to run business logic when a document is saved/submitted/cancelled? Yes Level 2 — Server Script via doc_events in hooks.py. Write unit tests.
Do I need to change the behaviour of an existing DocType's Python class? Yes Level 3a — Override the class. Import original, inherit, call super() first.
Do I need a completely new form/entity that doesn't exist in ERPNext? Yes Level 3b — New Custom DocType with Python controller. Link to existing DocTypes via Link fields.
Do I need an external-facing page, mobile interface, or third-party integration? Yes Level 4 — Custom page (Frappe UI), whitelisted API, or background job + integration connector.
Am I about to modify ERPNext source to add a feature? — Stop. There is always a correct way to do it from your custom app. Ask your team lead.
