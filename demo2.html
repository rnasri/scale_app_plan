AIWS ERP › HVAC Demo
🎬 Client Demo Story · starts from a real Sales Lead

Meridian Hospitality Group — Central Chiller Plant, Meridian Grand Pune

A second connected-project story, deliberately different from the existing Apex Manufacturing demo in one important way: this one starts from a cold Sales Lead, not an existing customer, and walks the entire real chain — Lead → Quotation → the Lead genuinely converting into a Customer → Sales Order → a Project created from that Sales Order → a genuine stock shortage → Material Request → Purchase Order approvals → Manufacturing. Every record below is real and live on this bench.

1 The Story

Meridian Hospitality Group is opening a new hotel, Meridian Grand, Pune, and needs a central chiller plant for the building. Their VP Facilities & Engineering, Ritika Shah, met AIWS Technologies at an HVAC/MEP trade exhibition and asked for a quote. That's a cold Lead — not yet a customer, not yet in the system as anything more than a name and a need.

Fulfilling the order that follows touches the same modules as any real project: Sales books and wins the deal, PMO runs it with a real team and a real kickoff, Manufacturing builds the chiller against a Bill of Materials and discovers a genuine shortfall, Purchase closes that shortfall through a proper multi-step approval, and Stock's own baseline receipt is what makes the shortfall real rather than staged.

Everything is tagged to one Project — PROJ-0076 · Meridian Grand Hotel — Central Chiller Plant — reachable end-to-end from its own Connections tab, the same native mechanism the Apex Manufacturing demo already relies on.

2 The Flow, Module by Module

Sales. A real Lead is created for Meridian Hospitality Group, converted to an Opportunity, and quoted — the Quotation is raised directly against the Lead (not a Customer, because none exists yet), with 3 real line items: 2× Air Cooled Screw Chiller (the item that gets a BOM and drives everything downstream), 6× a smaller Ductable Split AC unit (kept fully in stock on purpose — the contrast case that needs no purchasing at all), and a lump-sum HVAC Installation & Commissioning Services line. The Quotation is walked through Sales' own discount-approval workflow to Approved, and converting it into a Sales Order is the exact moment Scale's own native code turns the Lead into a real Customer record — nothing scripted around it, that's the actual mechanism.

PMO. The Project isn't created first this time — it's created from the Sales Order, using a native Scale mapper that the earlier Apex demo never exercised (that one built its Project before its Sales Order). It's then given a real Project Manager (Rohan Kapoor), a 5-person team cast into HVAC-appropriate roles for this one project, a Kickoff Checklist walked to PMO Approved, 6 real Tasks (Site Survey through Client Handover) each assigned to a specific team member, a Project Risk about the compressor vendor's lead time — linked directly to the real Supplier record, not just typed as a label — and 3 Budget Forecast Snapshots (Best/Expected/Worst case).

Stock. A deliberately partial raw-material receipt exists before Manufacturing ever runs — enough Compressor/Coil/Casing/Control Panel/Fan Motor/Refrigerant stock for exactly 1 of the 2 chillers ordered, so the shortfall Manufacturing's MRP engine finds for the second unit is real, not staged. The Split AC units, by contrast, are received in full — no shortage, nothing for Purchase to do there.

Manufacturing. A real Bill of Materials is built for the chiller (7 raw materials, 1 assembly operation). A Production Plan pulls the Sales Order's 2-chiller requirement through Scale's own native MRP engine, nets it against the genuinely partial Stock baseline, and computes an exact 1-unit shortfall — not a round number picked in advance. A Work Order for both chillers is raised and submitted, which automatically creates its own Job Card, logged with a real Time Log.

Purchase. The MRP-generated Material Request — tagged to the Project via the schema field PR #63 added just this week (its very first real use anywhere) — is converted into a Purchase Order against Precision Components India, an existing real supplier. Its value (₹5,77,600) deliberately clears the ₹5,00,000 approval threshold, so it walks the fuller branch of Purchase's own approval workflow — Submit → Approve → Forward to Management → Approve — rather than the shorter direct-approve path the Apex demo's own Purchase Order used. A full Goods Receipt then closes the shortage.

5 How This Was Built

Five small, idempotent seed scripts — one per app, run in this exact order (each depends on data the previous one creates), the same pattern the Apex Manufacturing demo established:

# Run once, in this exact order 1. bench --site <site> execute scale_stock.demo_project_seed_hvac.run 2. bench --site <site> execute scale_sales.demo_project_seed_hvac.run 3. bench --site <site> execute scale_project_management.demo_project_seed_hvac.run 4. bench --site <site> execute scale_manufacturing.demo_project_seed_hvac.run 5. bench --site <site> execute scale_purchase.demo_project_seed_hvac.run

Every script checks its own prerequisites and throws a named, actionable error rather than a raw link-validation failure if run out of order; every one is safe to re-run (checked live, several times, during this build). Nothing here changes the schema, adds a doctype, or touches a hook — it's pure data, exercising code that already exists.

✅ No blocking code gap found — the connectivity this story relies on already works

Sales Order → Project (native make_project() mapper), Lead → Customer conversion on Sales Order creation, and BOM → Production Plan → native MRP → Material Request → Purchase Order were all confirmed working by actually exercising them, not by reading the code and assuming. Two of Issue #62's brand-new fields (Material Request.pmo_project, Project Risk.vendor) got their first real data anywhere in this codebase as part of this build.

⚠️ One real gap found — worth fixing in the existing Apex demo script too

Building the Manufacturing leg surfaced a genuine gap in how Production Plan's native raw-material calculation actually works, not assumed from documentation: calling get_items() on a Sales-Order-sourced Production Plan only populates the "items to manufacture" table — it does not populate the raw-material requirement table that make_material_request() reads from. That needs a separate, explicit call to get_items_for_material_requests(), plus a for_warehouse field set on the plan so the netting calculation knows which warehouse's stock to check against. Skipping either step doesn't error — it silently either creates nothing, or requests the full gross quantity instead of the genuine shortfall.

The existing Apex Manufacturing story's own scale_manufacturing/demo_project_seed.py does not perform this step either. Its Material Request most likely survives today only because it was created once through a real Desk UI session, and that script's own idempotent "does it already exist" check has never re-exercised the creation path since — re-running it from a genuinely empty state would very likely produce zero Material Requests, not the one it currently points at. Worth a small follow-up fix there, mirroring the two-line fix applied in this story's own scale_manufacturing/demo_project_seed_hvac.py.
