C.2 — The Change-Test-Commit Cycle

Every task follows this loop. Do not skip the fixture export step — without it, a teammate who clones the repo and runs migrate will not get your changes.

  1. Make the change — in ERPNext UI (Customize Form / DocType / Workflow / Script) or in a Python file.
  2. Test it on your bench — create a test document, submit it, verify the behaviour is correct.
  3. Export fixtures (only for UI-made changes): bench --site <site> export-fixtures --app scale_hr
  4. Commit: git add apps/scale_hr/ → git commit -m "feat(hr): <description>"
  5. Push: git push origin main
  6. Notify team: after pull, they run bench --site <site> migrate to load DocType changes and fixtures.

When do teammates need bench migrate? Only when DocTypes changed (new field, new DocType, new workflow). Pure Python logic changes (hooks, tasks, ai_utils) only need bench restart. When in doubt, migrate — it's safe to run repeatedly.

C.3 — How to Add a Custom Field to an Existing DocType

Example: adding scale_hr_joining_source (Select) to the Employee DocType.

  1. Go to: ERPNext → Customize Form → DocType = Employee
  2. Scroll to the section where the field should appear. Click Add Row.
  3. Field Label: Joining Source · Field Name: scale_hr_joining_source · Field Type: Select · Module: Scale HR (critical — this makes it appear in fixtures)
  4. Add options in the Options box: one per line (e.g. Referral / Job Portal / Campus / Walk-in / Social Media).
  5. Save. The field appears on the Employee form immediately.
  6. Run: bench --site <site> export-fixtures --app scale_hr — the field is written to apps/scale_hr/scale_hr/fixtures/custom_field.json.
  7. Commit the fixtures file.

Rule: Always set Module = Scale HR on every custom field. Without it, the export filter misses it.

C.4 — How to Create a New DocType

Example: creating the Induction Plan DocType.

  1. Enable Developer Mode: bench --site <site> set-config developer_mode 1 then bench restart.
  2. Go to: ERPNext → DocType → New. Set Name: Induction Plan, Module: Scale HR, Is Submittable: yes (if you need submit/cancel), Track Changes: yes.
  3. Add all fields. For a child table, create a separate DocType first with Is Child Table checked, then link it with a Table field.
  4. Save. Frappe creates the JSON at apps/scale_hr/scale_hr/scale_hr/doctype/induction_plan/induction_plan.json automatically (because Developer Mode writes to the app folder).
  5. Run bench --site <site> migrate to create the DB table for the new DocType.
  6. Commit: git add apps/scale_hr/scale_hr/scale_hr/doctype/

Key difference from custom fields: Custom fields are exported as fixtures JSON. New DocTypes created in Developer Mode are saved directly into the app folder as JSON files — no fixture export needed. Both end up in git, but via different paths.

C.5 — How to Write a Python Hook

Example: auto-fetching employee assets on separation (for Exit Management).

# apps/scale_hr/scale_hr/exit_hooks.py

import frappe

def fetch_allocated_assets(doc, method=None):
    """Pull all assets assigned to employee into the F&F asset deduction rows."""
    assets = frappe.get_all(
        "Asset",
        filters={"custodian": doc.employee, "status": "In Location"},
        fields=["name", "asset_name", "purchase_amount"],
    )
    for asset in assets:
        doc.append("asset_deductions", {          # child table field name on your DocType
            "asset": asset.name,
            "asset_name": asset.asset_name,
            "deduction_amount": asset.purchase_amount,
        })

Then in hooks.py declare: "Employee Separation": {"before_submit": "scale_hr.exit_hooks.fetch_allocated_assets"}. After saving hooks.py, run bench restart — no migrate needed.
