2. What Veeren provided — SCALE_AI_DEV_BRIDGE.md

This is not a feature plan. It never mentions the NL Query chatbot, Lost Deal Analysis, or any V01–V08 task by name. It's a process document — how the AI team and the module-dev team share the same scale_sales codebase without stepping on each other. Explicitly scoped to be reused for scale_finance / scale_hr / scale_account later, the same way SCALE_DOMAIN_APP_PLAYBOOK.md was reused across modules for the dev-side build.

New mechanism it introduces: frappe_assistant_core (FAC)

AI capabilities get wrapped as BaseTool classes in a new fac_tools.py, registered via an assistant_tools key in hooks.py, and discovered by an AI client after a bench restart. The document's own worked example verifies a tool call through Claude Desktop — this is a tool-calling / MCP-style framework, not previously part of our plan in any form.

Rule of thumb (Veeren's, verbatim): the AI team can always ship logic that reads/writes through existing fields. The moment a feature needs a field or DocType that doesn't exist yet, it becomes a Dev-team PR, not an AI-team PR.

§3 — Delivery & sync workflow (as given)

  • Branch: feature/sales-ai-<topic> off main → PR into main
  • Daily sync (read-only, no gate): pull main, check demo_setup.py's T## comments for schema state
  • Build (no gate): logic in ai_utils.py; new tool = new BaseTool class in fac_tools.py
  • Discover + test: FAC picks up the tool after migrate + bench build + restart; verified via a live AI chat session against real site data
  • Flag (not gate): any hooks.py/tasks.py diff — CC dev lead, don't wait unless CODEOWNERS forces it
  • Propose + wait (real gate): new field/DocType need → a PR note or T##-style comment naming the exact field, the tool that needs it, and why. Dev team implements it as their own task.

3. Alignment analysis

✅ Confirmed aligned — no changes needed

  • Branch naming (feature/sales-ai-<topic>) matches our existing convention (feature/hrm, feature/muhammad-sales) — no clash.
  • The worked example wraps ai_utils.win_probability() — the exact rule-based function already shipped via the sales_demo → main merge. Confirms Veeren's team is extending, not rebuilding the live AI layer, exactly as we asked in the V06–V08 note on the Sales Module Plan.
  • The flagged gap — scale_sales_budget_confirmed missing on Opportunity — is the exact same known limitation already documented in apps/scale_sales/README.md. Independent confirmation from Veeren's side that the gap is real.

🆕 New from Veeren — better than what we had, recommend adopting as-is

  • The file-level ownership/gating map (§1). We never defined which files the AI team can touch without review vs. which need a Dev-team gate — this is genuinely useful and worth adopting verbatim for scale_sales, then reusing for scale_finance/scale_hr/scale_account exactly as the doc proposes.
  • The "Propose + wait" mechanism for schema gaps. Cleaner than anything we'd specified — it's effectively a formalization of what already happened organically with T18/T19/T20 during the PR #7 audit.
  • The concrete §2 setup TODOs (commit FAC registration, gate required_apps, add CODEOWNERS, document install) are real, actionable, and currently undone — see Recommended Path Forward below.

🚩 Open conflicts — need a decision before AI work starts using these

  1. Task-ID collision on "T18." Veeren's worked example has the Dev team implementing the new scale_sales_budget_confirmed field under a "T18" comment block in demo_setup.py. Our own, already-real T18 on the Sales Module Plan is a completely different task — "Wire a Real Customer Risk Rule + Build the Sales Config Screen." If Veeren's team starts using sequential T## numbering for AI-proposed schema needs, it collides with the numbering the dev side already uses (T18–T20 exist; T08 already carries an unresolved discount-rule conflict per the Sales Tracker). Recommend: AI-proposed schema needs get their own numbering — either prefixed (AI-T01, AI-T02…) or continuing after our highest existing ID (T21 onward) — confirmed with Veeren before his team's first PR actually touches demo_setup.py.
  2. Delivery surface for the NL Query chatbot (V01–V05) is undefined. Our plan builds a self-contained, hand-built chat widget on a custom "Sales Intelligence" Frappe Page inside the ERPNext UI, calling our own ai_query.answer() endpoint — no external client needed. Veeren's document verifies its FAC tools through an external AI client ("test tool call in Claude Desktop") — a fundamentally different delivery model (AI-agent-callable tools vs. an in-app widget), and it never mentions NL Query, V01–V05, or the chat widget at all. Two readings are possible: (a) FAC is purely additive infrastructure for developer/agent-callable tools like Win Probability, and the NL Query chatbot still gets built exactly as V01–V05 describe, independent of FAC — or (b) the NL Query interface itself is meant to be delivered as a FAC tool, in which case V04's custom widget may not be needed — but that would mean actual sales managers need an MCP-capable AI client connected to the site to ask a question, which doesn't fit "ask in plain English inside the ERP" as V04 describes it. This needs Veeren's confirmation before V03/V04-equivalent work starts — building the wrong one wastes real Wave-1 time.
