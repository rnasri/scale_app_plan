Manufacturing Module — Implementation Plan

Production for scale_manufacturing (client scope tab name: "Production"). Build started — Phase 1 (BOM/Work Order/consumption/output) confirmed live, third of the three new Supply Chain modules as planned, since it depends on both Stores and Purchase & Procurement (both now done) — its own spec remains the least mature of the three, with Phase 2's custom pieces still waiting on the missing PRD.

Open gap, flagged before any build starts: Unlike Purchase, there is no dedicated client PRD for Manufacturing in Claude/reference_from_team/ — only the one-line-per-feature "Production" tab in the Excel scope sheet (15 features, description + AI-enablement flag, no functional-requirements depth, no field lists, no report names). Per this project's own working rule ("verify against source PDFs/Excel — never build from a thin description if a real PRD should exist"), request a proper Manufacturing/Production PRD from the client or SIL team before Phase 2's custom pieces are built — Phase 1 (native BOM/Work Order/Job Card configuration) can safely start from the Excel description alone since it's ERPNext's best-covered native module (83% OOTB per module-plan.html's own estimate).

App: scale_manufacturing, own app, required_apps = [..., "scale_stock", "scale_purchase"] — needs both (BOM needs Items from Stores; MRP shortfalls raise Purchase Requests).

Why Manufacturing goes third: Its own scope sheet says so directly — Work Orders need Items (Stores) and Production Planning's MRP raises material shortfalls as Purchase Requests (Purchase). Building it last also buys time to get the missing PRD, so the custom pieces (Phase 2/3 below) are specified properly instead of guessed from one-line descriptions.

Module Objective

Turn a Bill of Materials and a sales/forecast demand signal into finished goods on the shelf — with raw-material consumption, machine/labour time, and scrap all costed accurately, and no work order started without knowing whether material and capacity actually exist.

Phase-by-Phase Implementation

Three phases following the make-to-stock flow. Phase 1 is the BOM→Work Order→consumption→output backbone. Phase 2 is quality/costing/capacity governance. Phase 3 is scheduling/reporting polish. Do not start Phase 2's custom pieces until the missing PRD (see banner above) is obtained — Phase 1 is safe to start on the Excel description alone since it's near-100% native configuration.

Phase 1 — Make-to-Stock Backbone

OOTB MFG-01 · Bill of Materials ▶

What already works: Multi-level, costed BOMs; ERPNext v16 Phantom BOMs for pass-through sub-assemblies that shouldn't be stocked as an intermediate item.

What to add: Nothing structural — this is pure master-data setup once Item master (Stores STR-01) exists. Confirm with the client whether Phantom BOM applies to any of their sub-assemblies before building the BOM tree.

OOTB MFG-02 · Process Routing ▶

What already works: Native Routing defines the operation sequence, workstations, and standard times — reused across products via BOM linkage.

What to add: Configuration only — build the actual routing templates from the client's real process once obtained (this is part of the missing-PRD gap: routing detail needs the client's actual operation sequence, not assumptions).

OOTB MFG-03 · Work Orders ▶

What already works: Full lifecycle with material binding and per-operation Job Cards at workstations.

Depends on: BOM (MFG-01) and Item/Warehouse (Stores STR-01/02) must exist first.

OOTB MFG-04 · Raw Material Consumption ▶

What already works: Transfer-for-manufacture and consumption entries against the Work Order, recorded at the moment they happen — same Stock Entry mechanism Stores already configures (STR-04).

OOTB MFG-05 · Finished Goods Output ▶

What already works: Manufacture Receipt brings FG into stock with batch/serial and true cost in one motion, closing the loop back into the same Stock Ledger Stores owns.

Phase 2 — Quality, Costing & Capacity Governance

OOTB MFG-06 · Quality Control ▶

What already works: Quality Inspection with templates for incoming (feeds Purchase's GRN), in-process (via Job Card), and outgoing inspection.

Needs from client (missing PRD gap): actual inspection parameters/templates per product line — not specified in the Excel one-liner.

OOTB MFG-07 · Batch / Job Costing ▶

What already works: Work Order costing — actual materials + operation time at workstation rates, with variance vs. standard cost visible natively.

Refine MFG-08 · Capacity Planning ▶

What already works: Workstation capacity is native.

What to add: A load-vs-capacity view and a pre-commitment "do we actually have the hours?" check before a Work Order is released — likely a Script Report over native Workstation/Job Card data, not a new DocType.

OOTB MFG-09 · Sub-contracting ▶

What already works: ERPNext's revamped subcontracting flow — material sent to vendor, finished parts received back, costs reconciled. Ties directly into Purchase's Supplier/PO flow for the vendor side.

Phase 3 — Scheduling & Reporting Polish

Custom MFG-10 · Machine Scheduling ▶

What already works: Job Card and Work Order both ship native Gantt views, including drag-to-reschedule and a generic Workstation filter — confirmed live, a real correction to the plan's assumption that scheduling visuals were entirely missing.

What was added: A new Machine Schedule Board page — the one genuine gap native coverage didn't close: the stock Gantt is a single flat list with no way to tell which machine a bar belongs to. The new board groups Job Cards into one Gantt lane per Workstation, filterable by date range and workstation, color-coded by status.

OOTB MFG-11 · Downtime Tracking ▶

What already works: Downtime Entry (Workstation + Operator, 7 preset reason codes + Other, auto-computed downtime duration) feeding a native Downtime Analysis report and dashboard chart.

One precision on the plan's wording: Downtime Entry links to Workstation and Employee only — there's no Job Card link on this doctype at all, despite the plan's "workstation/Job Card" phrasing. And there's no native "OEE" computation anywhere in the manufacturing module (zero references, checked directly) — what exists is downtime/availability reporting, not a full Availability×Performance×Quality OEE metric. That gap is already correctly captured separately under MFG-13/14.

OOTB MFG-12 · Scrap & Waste Management ▶

What already works: BOM Scrap Items table plus automatic process-loss accounting on the Manufacture Stock Entry — waste is costed automatically and netted out of the finished good's cost, not a manual write-off.

Custom MFG-13 · Shift Management ▶

What already works: Shift Type / Shift Assignment are native, shared with HR — confirmed live there's zero linkage anywhere to production data: no shift field exists on Job Card, Job Card Time Log, or Downtime Entry.

What was added: A new Shift Production Report that buckets existing Job Card Time Log and Downtime Entry timestamps into each Shift Type's time-of-day window — including overnight shifts that cross midnight — with zero new fields on those doctypes, plus a new Shift Handover Note DocType for the outgoing supervisor's notes.

OOTB MFG-14 · Production Reports ▶

What already works: Far more than "native operational reports" suggested — a full native reporting suite already covers plan-vs-actual (Work Order Summary, BOM Variance Report), trends (Production Analytics), and exceptions (Cost of Poor Quality Report, Process Loss Report, plus MFG-11's Downtime Analysis). None of it was surfaced anywhere in this app's own workspace until now — surfaced as Reports-card links, config only, no new code.

Deliberately not built: a computed "OEE" trend chart. No native OEE metric exists anywhere in the module (confirmed at MFG-11), and a defensible one needs client-specific inputs — ideal cycle time, quality rejection thresholds — that don't exist in any source document. Same missing-PRD class as MFG-02/06, not a Wave 4 Dashboards timing issue; not inventing a formula nobody asked for.

OOTB MFG-15 · Production Planning (MRP) ▶

What already works: Production Plan built from Sales Orders, with MRP — material shortfalls become real Material Requests automatically. Confirmed live end to end, not just read from the plan: a Sales Order for 5 finished goods (needing 10 units of raw material via the BOM, with only 2 in stock) correctly produced an 8-unit shortfall, which the native MRP engine turned into a submitted, Purchase-type Material Request in "Pending" status — the exact native doctype and state Purchase's own PUR-01 (Purchase Requisition) flow already consumes. This is the direct integration point into Purchase's Inventory Procurement Planning (PUR-13).

Sequenced last in Phase 1's logical flow (numbered 15, not 6, in the build list) because it's the one feature that needs BOM, Work Order, and a working Purchase Requisition flow (PUR-01) all in place before it can be tested end-to-end — it's the integration proof point across all three new modules, not a standalone config task. All three were in place by the time this was tested, so the full chain was verified for real.

Task List

One task per feature, in build order. No dates assigned yet (see Open Decisions) — and several tasks below are explicitly blocked on the missing PRD, not just on lead assignment.

MFG-01

BOM setup

✅ Done
Effort: Medium · Depends on: Stores STR-01 (Item master)

Confirmed live with a real 2-level BOM (raw material → sub-assembly → finished good): multi-level cost roll-up correctly propagated through both levels (a sub-assembly costed via its own submitted BOM was picked up automatically when costing the parent). Real correction to the plan, found while testing: "ERPNext v16 Phantom BOM" (pass-through sub-assemblies that skip stocking an intermediate item) does not exist on this bench's actual ERPNext version (15.118.1) — grepped the entire manufacturing module for "phantom," zero hits anywhere. If the client genuinely needs it, that's a version upgrade, not something this app can add on top. Also confirmed native BOM costing reads from an item's actual valuation history ("Rate Of Materials Based On" defaults to Valuation Rate, no "Manual" option exists on this version) — a brand-new item needs a real opening stock transaction before its BOM cost will show anything other than zero, not just a typed-in rate.

MFG-02

Process Routing setup

⏸ Blocked on PRD
Effort: Medium · Blocked on PRD — needs client's real operation sequence

Not started, not skipped by accident — the native Routing/Operation mechanism itself is confirmed native (same as every other Phase 1 piece), but building real templates needs the client's actual process sequence, which doesn't exist in any source document yet (see the module's own open-gap banner above).

MFG-03

Work Order configuration

✅ Done
Effort: Low · Depends on: MFG-01, MFG-02

Confirmed live against the same 2-level BOM used for MFG-01: Work Order's own required_items correctly explodes all the way down to the raw-material level (6 units of raw steel for 1 finished good needing 3 sub-assemblies × 2 raw each), not just the immediate sub-assembly — multi-level BOM support holds at the Work Order layer too, not only in BOM costing. Didn't end up depending on MFG-02 in practice, since a Work Order can be raised and worked without a Routing attached (Routing only matters once operation-level Job Cards are needed).

MFG-04

Raw material consumption flow

✅ Done
Effort: Low · Depends on: Stores STR-04

Confirmed live: a Manufacture-type Stock Entry against the Work Order correctly consumed the sub-assembly from stock and posted the finished good in the same transaction — the standard Stock Entry mechanism Stores already configures (STR-04), reused as-is.

MFG-05

Finished Goods receipt flow

✅ Done
Effort: Low

Confirmed live in the same test as MFG-04: the finished good posted correctly to the target warehouse with the right quantity, and the Work Order's own status correctly moved to Completed with the right produced_qty — closing the loop back into Stores' own Stock Ledger.

MFG-06

Quality Inspection templates

Effort: Medium · Blocked on PRD — needs client's actual QC parameters

Build incoming/in-process/outgoing inspection templates once inspection criteria are confirmed.

MFG-07

Work Order costing verification

✅ Done
Effort: Low

Confirmed live with a real Workstation (₹600/hour), a BOM with one costed operation (60 planned minutes), and a Job Card logging 90 actual minutes: Work Order's planned_operating_cost (₹600) and actual_operating_cost (₹900) both computed correctly and sit side by side on the same document — a genuine ₹300 cost overrun, visible the moment the Job Card is submitted. One precision on the plan's own wording: there's no dedicated "variance" field or report — it's two real numbers on the same doc that a report/reviewer subtracts themselves, not a computed percentage shown automatically. Real API gotcha caught live, doesn't affect real usage: Work Order's operations/required_items tables do NOT auto-populate from bom_no on a plain insert — the Desk UI itself fires the whitelisted get_items_and_operations_from_bom() call the moment a user picks a BOM, so a real user never hits this; it only bit a script inserting a Work Order directly via the API.

MFG-08

Capacity load-vs-capacity report

✅ Done
Effort: Medium · New Script Report

Real discovery, plan was wrong on half of this: the pre-commitment "do we actually have the hours?" check the plan called out as missing is already fully native and enabled by default on this bench (Manufacturing Settings.disable_capacity_planning = 0) — confirmed live by scheduling two overlapping Job Cards on a capacity=1 Workstation and watching the second one genuinely get rejected with a real error, no configuration needed. The one real gap: nothing showed how much capacity was already booked over a date range before deciding whether to release a new Work Order. New Workstation Capacity Load report computes Available Hours (daily working-hours total × production capacity × non-holiday days in the filtered range) against Booked Hours (actual Job Card time logged in that range), with a Utilization % and an Available / Near Capacity / Over-Committed status. Real bug caught and fixed while building: Workstation has no company field at all — the first version filtered on it directly and threw a SQL error; deliberately left uncorrected as a company filter afterward too, since scoping via Workstation's optional warehouse link would silently exclude any workstation that doesn't have one set (common, since that field is only used for scrap/output tracking). Tested live: the available-hours formula (8hrs/day × capacity 2 × 1 day = 16 hours, 2 hours booked → 12.5% utilization, correctly "Available") and holiday exclusion (5 calendar days with 1 holiday = 4 working days × 8hrs = 32 available hours) both verified separately.

MFG-09

Sub-contracting configuration

✅ Done
Effort: Low · Depends on: Purchase PUR-02/03

Confirmed live end-to-end on ERPNext's revamped subcontracting flow: a finished good flagged is_sub_contracted_item, linked via a Subcontracting BOM to its raw-material BOM and a service item, ordered on a subcontracted Purchase Order, converted to a Subcontracting Order (auto-computing 2 raw units needed per finished good from the BOM), raw material transferred to a genuinely separate supplier warehouse via a "Send to Subcontractor" Stock Entry, and received back via Subcontracting Receipt with cost correctly reconciled as service charge + consumed raw material (₹100 + ₹40 = ₹140) — exactly matching the BOM + PO rate inputs, no manual cost entry anywhere in the chain. Zero code needed. Two real API gotchas caught live, don't affect real Desk usage: the finished good's is_sub_contracted_item flag isn't implied by anything else and must be set explicitly; and the transfer Stock Entry's item row needs an explicit subcontracted_item link back to the finished good or the system can't match it against the Subcontracting Order's own Raw Materials Supplied table — the Desk UI sets this automatically when a user picks the SCO, so only a script inserting the Stock Entry directly via the API hits it.

MFG-10

Machine Scheduling board

✅ Done
Effort: Medium · New UI (custom Desk Page)

Confirmed live first that ERPNext already ships native Gantt views for both Job Card and Work Order — including working drag-to-reschedule and a generic Workstation filter, both verified in the browser — a real correction to the plan's assumption that scheduling visuals didn't exist yet. Real defect found in native config, doesn't break anything: Job Card's own calendar/gantt config (job_card_calendar.js) references subject/color/allDay/progress fields that don't exist anywhere on the Job Card doctype — confirmed by dumping its full fieldlist. Verified live it still renders correctly regardless, since Frappe falls back to the doctype's title_field for the bar label and silently no-ops on the missing color/progress fields — a harmless dead reference, not a functional bug. The one real gap native coverage left open: the stock Gantt is a single flat list with no way to tell which machine a bar belongs to. Built a new Machine Schedule Board page (reusing Frappe's own bundled frappe-gantt library, same technique the native views use, zero new dependencies) that groups Job Cards into one Gantt lane per Workstation — filterable by date range and Workstation, colored by status (Open/In Progress/On Hold/Completed/Cancelled). Tested live with 2 workstations and overlapping job cards: correct per-machine grouping, correct status coloring, Workstation filter correctly narrows to a single machine's lane. Bar-click navigation to the Job Card form was checked against the native Gantt view too for a fair comparison — both have the same real-world limit of frappe-gantt's thin-bar click target on short-duration jobs; not a regression introduced here.

MFG-11

Downtime Entry + OEE feed

✅ Done
Effort: Low

Confirmed live: a Downtime Entry against a real Workstation with a preset reason code ("Machine malfunction") correctly auto-computed its own duration (45 minutes, from/to time diff) on save, and immediately showed up correctly in the native Downtime Analysis Script Report (0.75 hours, workstation-scoped filter honored) with its bar chart aggregating downtime by machine. Zero code needed. Real precision, not a gap: confirmed by dumping the doctype's full fieldlist that Downtime Entry links to Workstation + Employee only, no Job Card field exists at all, correcting the plan's "workstation/Job Card" phrasing. Also confirmed there is no native "OEE" computation anywhere in the manufacturing module (grepped for it directly, zero hits) — what's native is downtime/availability reporting, not a full Availability×Performance×Quality OEE metric; that real gap stays out of scope across MFG-13 and MFG-14 too — both build shift/production reporting, neither invents an OEE formula, since a defensible one needs client-specific inputs no source document defines.

MFG-12

Scrap/waste configuration

✅ Done
Effort: Low

Confirmed live: a BOM Scrap Item (1 unit, ₹10 estimated rate) auto-populated into a real Manufacture Stock Entry with zero manual entry, landed correctly in the Work Order's Scrap Warehouse, and the finished good's cost came out correctly netted (₹200 raw material − ₹10 scrap value = ₹190), not the full raw-material cost. Zero code needed. Real correction, consistent with a pattern already found in MFG-01: a brand-new scrap item's BOM-level "rate" is only an estimate for the BOM's own scrap_material_cost display — it does not carry through as the real transaction's valuation rate. A scrap item still needs its own real stock/valuation history (or Allow Zero Valuation Rate) before a live Manufacture entry will value it correctly, same "typed rate ≠ real valuation" rule already documented for BOM costing. Also confirmed the Work Order needs an explicit Scrap Warehouse set, or the scrap row has no target warehouse and the entry is blocked — a real setup requirement, not a bug.

MFG-13

Shift-wise OEE reporting

✅ Done
Effort: Medium · Depends on: HR shift types

Confirmed live first that Shift Type / Shift Assignment are genuinely native (shared with HR) but carry zero linkage to production data anywhere — no shift field exists on Job Card, Job Card Time Log, or Downtime Entry. That's the real gap this closes, without adding any new fields to those doctypes. New Shift Production Report buckets Job Card Time Log and Downtime Entry timestamps into each Shift Type's own time-of-day window (start_time/end_time), including overnight shifts that cross midnight, aggregating output qty and downtime hours per Shift × Workstation. Tested live with a real day shift (06:00–14:00) and a midnight-crossing night shift (22:00–06:00) on the same Workstation: a 5-unit Job Card logged at 08:00 and a 3-unit Job Card logged at 23:00 landed in the correct day/night buckets respectively, and a downtime event at 23:30 correctly landed in the night bucket too — confirming the overnight-wrap logic works, not just the simple case. New Shift Handover Note DocType (Workstation, Shift, Handover Date, Handed Over By/To, Output Summary, Pending Items, Notes) gives the outgoing supervisor a simple log for the next shift, since native Frappe has no handover mechanism of any kind. One precision on the plan's wording: this report computes output and downtime by shift, not a full OEE percentage — same boundary already established in MFG-11 and carried into MFG-14, no source document defines the inputs a defensible OEE formula would need.

MFG-14

Production reports assembly

✅ Done
Effort: Low (config only) · Feeds Wave 4 Dashboards

Confirmed live first — a real survey of ERPNext's own manufacturing report directory, not just reading the plan's one-liner — that plan-vs-actual and exception views are already comprehensively native: Work Order Summary (planned vs. actual start/end dates, lead time, produced qty), BOM Variance Report (ordered vs. produced qty, required vs. consumed qty per raw material), Process Loss Report (FG value vs. RM value, process loss qty), Production Analytics (period-by-period Work Order status trend with a chart), and Cost of Poor Quality Report (rework cost via corrective operations) — none of it new code, all of it just not surfaced anywhere in scale_manufacturing's own workspace before this. Added all 5 as Reports-card links (workspace config only, verified each opens cleanly in the browser after migrate). Deliberately not built: an "OEE trend" chart — no native OEE metric exists anywhere (confirmed at MFG-11), and computing a defensible one needs client-specific inputs (ideal cycle time, quality thresholds) no source document defines. That's the same missing-PRD class as MFG-02/06, not a Wave 4 timing gate — not inventing an unrequested formula, same discipline already applied at Purchase's PUR-14 (Cost Savings/ROI deliberately not built there either).

MFG-15

Production Planning / MRP integration test

✅ Done
Effort: Medium-High · Depends on: MFG-01–05, Purchase PUR-01, Stores STR-01/09/13

Confirmed live, full chain, no code needed anywhere: created a Sales Order for 5 units of a finished good on a real 2-level-costed BOM (2 raw material units per finished good, so 10 units needed), with deliberately only 2 units of raw material in stock to force a genuine shortfall. Raised a Production Plan from that Sales Order (get_items_from = "Sales Order"), called the native MRP engine (get_items_for_material_requests — the same whitelisted method the Desk UI itself calls), and it correctly computed an 8-unit shortfall (10 needed − 2 in stock). Populated the Production Plan's own mr_items table from that result and called make_material_request(): a real, submittable Material Request was created, defaulting to type "Purchase," which submitted cleanly to status "Pending" — the exact native doctype and state Purchase's own PUR-01 (Purchase Requisition) flow already consumes, closing the loop for real rather than by inspection. This is the last feature in the entire 15-item Manufacturing plan; only MFG-02 and MFG-06 remain, both permanently parked pending the missing Manufacturing PRD.

Open Decisions

Request a Manufacturing/Production PRD

The single biggest open item for this module. Purchase & Procurement had a 15-page PRD; Stores had a fully fit-gap-annotated Excel tab; Production has neither. Routing (MFG-02) and Quality Inspection templates (MFG-06) both need it before Phase 2 custom work should start. (The Machine Scheduling board, MFG-10, turned out not to need it — the real gap was small and self-evident once native Gantt coverage was checked directly.)

Lead & start date not yet assigned

Same as Stores/Purchase — Wave 2, Lead: TBD in module-plan.html. Given the dependency chain, Manufacturing's real start date should trail Stores/Purchase's, not run in strict parallel with them.
