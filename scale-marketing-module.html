Module Objective

This app is the connector between Scale ERP's Lead/Customer data and two external channels: WhatsApp (Meta Cloud API) for conversational sales/support, and Meta Ads (Marketing API) for paid social lead generation. It is a distinct app from scale_sales (the core CRM/pipeline app) — this page tracks its own build separately, since it had no dedicated tracking page until this update.

⚠ This page was created retroactively

The app existed and shipped real features (PR #37, #38) before this page did. This page was created 25 Aug 2026 once the scope grew enough (multi-number WhatsApp, access control, Meta Ads) to warrant its own tracked plan, matching the convention every other scale_* app already has. Earlier WhatsApp work (inbox, automations, bookings, drips) is documented here from a direct code review, not from original build notes — flag anything that reads inaccurately against what was actually built.

Feature Area 1 — WhatsApp Core

PR #37 → #38, merged 23 Aug 2026

M01 WhatsApp Inbox, Automations, Bookings, Drips Muhammad Done — 23 Aug 2026
app: scale_sales_marketing · doctypes: Scale WhatsApp Conversation, Scale WhatsApp Message, Scale WhatsApp Appointment, Scale WhatsApp Booking Settings

What shipped: Full inbound/outbound WhatsApp messaging via the Meta Cloud API — webhook receiver, conversation threading, template-based replies (required outside the 24-hour free-text window), appointment booking flow, drip campaigns, and a scheduled reminder job. Reviewed across 2 PR rounds; found and confirmed-fixed a webhook signature fail-open bug (missing signature header was being treated as valid) before merge.

  1. whatsapp/webhook.py — the whitelisted, guest-accessible entrypoint (allow_guest=True). Verifies X-Hub-Signature-256/X-Hub-Signature via HMAC (hmac.compare_digest) before touching the payload — fails closed if a secret is configured but the header is missing.
  2. whatsapp/inbox.py — desk-side API surface: list_conversations, get_thread, reply, reply_template, convert_to_lead.
  3. whatsapp/automations.py, bookings.py, drips.py, scheduler.py — inbound message handling, appointment booking state machine, drip sequencing, and the per-minute cron jobs (process_drips, process_appointment_reminders, cleanup_sessions).

Feature Area 2 — Multi-Number WhatsApp + Access Control

PR #42 "Add Scale Marketing module and enhance WhatsApp integration", merged 25 Aug 2026

M02 Multi-Number WhatsApp Routing Muhammad Done — 25 Aug 2026
Deliverable: a business can connect several WhatsApp numbers to one site, each tracked and permissioned separately

Why this exists: The original build (M01) assumed one WhatsApp number per site. A business running multiple numbers (e.g. one per region or one per brand) had no way to keep those conversations, and the staff who handle them, separate.

  1. Conversation naming now embeds the sending number: wa_{phone_number_id}_{customer} instead of a bare wa_{customer} — confirmed in store.py::conversation_name().
  2. Inbound webhook payloads route by Meta's own metadata.phone_number_id field — is_phone_enabled() checks it against the discovered/active phone list (or the configured default) and fails closed for unrecognized numbers, so a message from an unconfigured number is never silently attributed to the wrong one.
  3. Meta Connect page can discover and enable several numbers per WABA (WhatsApp Business Account) and designate one as default sender.
M03 Number-Scoped Access Control Muhammad Done — 25 Aug 2026
New doctype: Scale WhatsApp Number User (user + phone_number_id) · new file: whatsapp/access.py

Rule: System Manager / Sales Manager / Administrator see every number. Anyone else only sees the numbers explicitly assigned to them via Scale WhatsApp Number User — an empty assignment means zero WhatsApp conversations visible (Facebook/Instagram inbox items still show, since those aren't number-scoped).

Reviewed directly, not taken on faith: this is enforced in three independent layers, not one — checked each personally before recommending merge.

  1. List-level: conversation_list_filters() builds the actual frappe.get_all filter/or_filters — a restricted user's inbox query is filtered server-side, not just hidden in the UI.
  2. ORM-level: permission_query_conditions and has_permission both registered in hooks.py for Scale WhatsApp Conversation and Scale WhatsApp Appointment — this is Frappe's own native permission system, so even a raw frappe.get_doc respects the number scoping.
  3. API-level: every single-conversation endpoint (get_thread, list_messages, reply, reply_template, convert_to_lead) calls assert_conversation_access() before doing anything — closes the path where a restricted user could otherwise guess/enumerate a conversation name outside their assigned numbers and read or reply to it directly, bypassing the list filter.
This is a more rigorous permission pattern than some earlier findings elsewhere in this codebase (e.g. PMO's milestone-approval action, which originally had UI-only gating with no server-side check). Worth treating as the reference implementation for "how to do number/record-scoped access control" going forward.
M04 User Account Management Overhaul Muhammad Done — 25 Aug 2026
app: scale_sales · access_control.py (377-line diff) + user_account_management_page.js (644-line diff)

What shipped: a custom role-picker replacing Frappe's own MultiCheck (which had a "Select All" flip bug), a "show password once" flow on user create/reset, and a Permissions tab covering Sales + Marketing DocTypes and Pages via Custom Role.

  1. Every sensitive endpoint (create_user, update_user, set_user_roles, delete_user, create_role, set_role_doctype_perms, set_role_permission_bundle, set_page_role) calls _require_admin() first — verified individually, all present, none skipped. Administrator/Guest are explicitly protected from being modified through this UI.
  2. Generated passwords are cached client-side in sessionStorage only (cleared on tab close, never transmitted anywhere beyond the initial create/reset call) so an admin can re-copy credentials within the same session without re-generating — a UX convenience, not a new secret store.
  3. Save writes Has Role directly rather than relying on the picker's own checkbox state, so an unchecked role reliably stays off — the bug this was built to fix.

Feature Area 3 — Meta Ad Calendar & Boost Post

PR #41 "Meta ad calendar, boost post, and link ad launch", merged 25 Aug 2026

M05 Ad Calendar + Scheduled Publishing Archit Done — 25 Aug 2026
New doctype: Scale Ad Calendar · new page: Ad Calendar View (month grid) · new cron: process_due_ads

What shipped: a month-grid calendar UI for planning ad posts, a scheduled job that auto-launches ads at their scheduled time via the Meta Marketing API, Boost Post (promote an existing Scale Social Post / calendar entry), and single-image Link Ad launch with ad-account sync on connect.

  1. marketing/ads/client.py, creative.py, launch.py — the Marketing API layer. Reuses whatsapp/oauth.py's existing token/secret storage rather than introducing a second credential mechanism.
  2. process_due_ads() (added to the same per-minute cron as WhatsApp's process_due_posts) has proper per-record isolation — try/except + frappe.db.rollback() + frappe.log_error() per ad, so one bad ad can't stall the rest of the scheduled batch.
  3. install.py::import_meta_settings_bootstrap() — a local-dev credential loader that reads from sites/<site>/private/scale_meta_bootstrap.json (explicitly git-ignored, never committed). Confirmed not wired into after_migrate, so it can't break a developer who doesn't have that private file.
✓ Merge conflict — found, analyzed, resolved

PR #41 and PR #42 were developed in parallel and both added the same new "scale_sales_marketing" entry to apps/scale/scale/app_sidebar.py's SCALE_APP_SIDEBARS dict — same 3 fields on both sides, but PR #42's version additionally included a path_prefixes list (9 desk routes: inbox, appointments, leads, templates, bot settings, flows, meta-connect, meta-leads). Traced path_prefixes to scale_app_sidebar.js before resolving — it drives which routes highlight the Scale Marketing sidebar entry as active, so it's a real behavioral difference, not cosmetic. PR #42 merged first (landing the fuller version on main); when PR #41 then showed CONFLICTING, resolved by keeping PR #42's superset and discarding PR #41's shorter duplicate — verified via bench migrate (clean) before pushing the resolution and merging.

Architecture Notes

  • One token store, reused everywhere. Both WhatsApp and Meta Ads authenticate through the same whatsapp/oauth.py module (user_token(), app_credentials()) — no separate credential system was built for the Ads side.
  • Permission pattern to copy for future number/record-scoped features: list-filter + native permission_query_conditions/has_permission + explicit API-level assertion, three layers, all independently verified — see M03 above.
  • Local-dev credential bootstrap pattern: a private, git-ignored JSON file under sites/<site>/private/, loaded by an explicit manual command — never auto-run on migrate. Same shape as any future integration needing per-developer secrets.
  • No sites/apps.txt, apps.json, or common_site_config.json changes in either PR — avoids the exact class of corruption this repo has been bitten by before (see Claude/TECHNICAL_CONTEXT.md §3).
