System Architecture

How the custom apps are structured, how multi-tenancy works, how data flows, and how the system will be deployed at scale.

The custom app family

All AIWS-specific code lives in custom Frappe apps installed on top of the standard ERPNext stack. Each app is an independent pip package with its own Git repository, version, and release cycle. This is the only correct way to build on Frappe without forking.

Multi-tenancy model

Frappe's native multi-tenancy is site-per-tenant. Each client gets their own Frappe site with a dedicated MariaDB database. All sites on a bench share the same app code — they install from the same apps — but have completely isolated data.

Tier A — Pooled SaaS (default)

Multiple client sites on one bench cluster. Cheapest to operate — 4–8× lower cost than dedicated. Frappe Cloud manages this for you if you use their hosting. Self-managed on AWS EKS with frappe_docker otherwise.

When to use: All new clients by default. SMB and mid-market.

Isolation: Database-level (separate MariaDB DB per site). App-level code is shared.

Tier B — Dedicated (enterprise)

One client per bench cluster (or per VM). Full isolation at the infrastructure level. Same codebase — same apps, same version — but the client gets their own server.

When to use: Enterprise clients with compliance requirements or high data sensitivity.

Migration path: Tier A → Tier B via bench --site sitename backup + restore on a new bench.

Control plane (future): A separate Python/FastAPI service (not part of this ERP build) will serve as the tenant registry and provisioning API — tracking which clients exist, which tier they're on, and automating site creation. For now, a spreadsheet or simple admin script suffices. Design the scale_core AIWS Config Profile DocType as the future control-plane "write surface."

API surface

Auto-generated REST APIs

Every DocType in ERPNext and your custom apps automatically gets CRUD REST APIs at:

Endpoint pattern
/api/resource/{DocType}/{name}   GET, PUT, DELETE
/api/resource/{DocType}          GET (list), POST (create)
/api/v2/document/{DocType}/{name}

These are authenticated via session cookie or API key/secret. No extra work needed.

Custom whitelisted APIs

For complex business operations, expose custom Python functions via the @frappe.whitelist() decorator:

Python — custom API
import frappe

@frappe.whitelist()
def get_dealer_scorecard(dealer_id, period):
    # complex business logic
    return frappe.db.sql("...")

Called at: /api/method/scale_sales.api.dealer.get_dealer_scorecard

Deployment model

EnvironmentHow to runNotes
Local development bench start on a local bench, or docker compose up with frappe_docker Each developer maintains their own local bench with a dev site. See Developer Workflow.
CI/CD GitHub Actions — run bench run-tests --app scale_sales on every PR Use frappe/frappe_docker as the CI base image. Tests run against a fresh site.
Staging Single AWS EC2 instance (t3.medium) or Frappe Cloud dev environment Mirror of production; all migrations tested here first. Dedicated staging site per module team.
Production — SaaS AWS EKS cluster using frappe_docker Helm chart, or Frappe Cloud (managed) Recommended: Frappe Cloud for MVP/early clients (managed updates, backups, monitoring). Move to self-managed AWS when scale justifies it.
Production — On-prem Customer-hosted Docker Compose or single VM bench Ship an installation script and Docker Compose file. Customer gets a support SLA for updates.

Recommendation for early stage: Start with Frappe Cloud for the first wave of clients. It handles infrastructure, SSL, backups, and bench updates. Once you have 10+ clients, evaluate migrating to self-managed AWS EKS to reduce per-client infrastructure cost. Don't prematurely optimize infrastructure.
