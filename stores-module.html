Stores Module — Implementation Plan

Inventory & Warehouse Management for scale_stock. Not started — this is the pre-build plan (feature map + task list), same stage Sales/HR/PMO were at before their kick-off. Recommended as the first of the three new Supply Chain modules to build.

App: scale_stock, own app, depends only on F0 (scale + ERPNext) — the base of the dependency chain. scale_purchase and scale_manufacturing both declare required_apps = [..., "scale_stock"].

Why Stores goes first: Item, UOM, Warehouse, and the Stock Ledger are the shared foundation every other module in the suite reads from — Sales delivery notes, Purchase goods receipts, and Manufacturing work orders all post against this same ledger. Per the source scope document (_PIXAFLIP_ SCALE_ERP Modules Scope and Capability.xlsx, "Stores" tab), 13 of 13 features are already fit-gap analysed line-by-line with a "Frappe Support / Standard Flow / Implementation Needed" verdict — nearly all of it is 100% native ERPNext, zero custom code. It is the lowest-risk, fastest module to stand up, and Purchase's Goods Receipt and Manufacturing's BOM/Work Order both need it configured first. See Purchase & Procurement and Manufacturing for how they build on top of this.

Module Objective

Provide a single, live, always-correct view of stock — what is on hand, where, what it's worth, and what's committed — so Sales can promise real availability, Purchase knows what to reorder, and Manufacturing can trust the raw-material numbers it plans against. Every stock-moving transaction in every other module (Delivery Note, Purchase Receipt, Stock Entry) settles here, in the same Stock Ledger, using the same Item/Warehouse masters.

Phase-by-Phase Implementation

Three phases. Phase 1 is pure configuration — Item/Warehouse/UOM setup, no code — and unblocks Purchase (needs Warehouse + Item to receive against) and Manufacturing (needs Item for BOM) immediately. Phase 2 adds the handful of genuinely custom pieces. Phase 3 is post-go-live polish, safe to defer.

Phase 1 — Master Data & Native Configuration

Everything here is configuration in the admin UI. Zero custom code. This is the critical path for every other Supply Chain module.

OOTB STR-01 · Item Master ▶

What already works: Item, Item Group, UOM, UOM Conversion Detail, Item Attribute/Variants, and Item Supplier DocTypes — one shared master record used by Stock, Purchase, Sales, Accounts, and Production simultaneously.

To configure: Item Group tree per the client's product taxonomy, default UOM + conversion factors, barcodes, Item Attribute templates for variants (if any variant-based items exist), Item Price lists. Zero custom fields expected unless a client-specific attribute surfaces during build.

Why it's first: Purchase Orders, BOMs, and Sales Items all resolve to this one record — get the Item Group taxonomy right before any transactional module starts, since renaming/regrouping later touches every module.

OOTB STR-02 · Stock Management ▶

What already works: Live Stock Ledger (Stock Ledger Entry) with bin-level quantities (Bin: actual/reserved/projected qty) per Item × Warehouse. Every stock-moving transaction across every module auto-posts here.

To configure: Stock Settings defaults (valuation method, auto-insert price list rate, allow negative stock — off by default). No custom code.

OOTB STR-03 · Multi-location / Warehouse ▶

What already works: Warehouse tree DocType (parent group → child leaf, e.g. Plant → Building → Rack), each leaf mapped to a Stock Account, transactions post to leaf nodes and roll up to parent group in reporting automatically.

To configure: Build the actual warehouse hierarchy for the client's site(s) — this needs the real facility layout, so confirm with the client before this task starts.

OOTB STR-04 · Goods Issue / Receipt ▶

What already works: Stock Entry (Material Issue / Material Receipt / Manufacture purposes), Purchase Receipt, Delivery Note — every one auto-creates a Stock Ledger Entry and the matching GL Entry (Stock In Hand vs. Adjustment/Expense/COGS account) on submit.

To configure: Stock Entry Purpose rules, default Stock/Adjustment accounts per warehouse, submit-approval workflow if the client wants issue/receipt sign-off.

OOTB STR-05 · Inventory Valuation ▶

What already works: FIFO / Moving Average valuation per Item (Stock Settings), Landed Cost Voucher for freight/duty/insurance apportionment, and the perpetual-inventory GL engine that auto-posts Stock-in-Hand vs. COGS/Expense on every movement.

To configure: Choose valuation method per Item Category with Finance sign-off (affects COGS and margin reporting — coordinate with the Accounts/Finance tracks before locking this in).

Phase 2 — Refinement & the Two Genuinely Custom Pieces

Small, native-first extensions. Only two new DocTypes in this entire module.

Refine STR-06 · Stock Transfers ▶

Approach: Native 2-step transfer using an intermediate In-Transit Warehouse (Stock Entry: Material Transfer → submit at source → receive/submit at destination). Add a ~15-line JS Client Script to capture driver and vehicle details on the Stock Entry form for inter-site transfers.

Refine STR-07 · Barcode / QR Scanning ▶

Approach: Native Item Barcode child table + the scan_barcode input already present on Stock Entry / Purchase Receipt / Delivery Note / Stock Reconciliation — scanning auto-increments the matched row's qty. Add a ~20-line HTML5 camera QR/barcode scanner script for mobile-browser use in the store room (no native app, no hardware dependency required for go-live; a Bluetooth handheld scanner can be added later without any schema change).

Custom STR-08 · Stock Audit / Cycle Count ▶

Approach: Native Stock Reconciliation (with scan mode) already handles the variance-posting side. Add one custom DocType, Cycle Count Sheet, for scheduled/ABC-based blind counting — it hides the system quantity until the counter enters their physical count, then reconciles the delta into a standard Stock Reconciliation. This is the one piece the native flow doesn't cover (open counting, where the counter can see the system qty and rubber-stamp it, defeats the point of an audit).

Custom STR-09 · Slow & Non-moving Stock ▶

Approach: Native Stock Ageing report (0–30 / 30–60 / 60–90 / 90+ day buckets) already identifies what's slow-moving. Add one custom DocType, Stock Disposition Request, with a standard Frappe Workflow (Stores raises → Finance approves) — approval auto-triggers a Stock Entry (Material Issue / Scrapped). This is the decision layer the native report doesn't have: someone has to actually decide discount, return, or write-off, and that decision needs an audit trail.

Phase 3 — Post-Go-Live Traceability & Planning (defer without risk)

All native, all zero custom code. Sequenced last only because the client's own scope sheet schedules them P3 — none of it blocks Purchase or Manufacturing starting.

OOTB STR-10 · Reorder Alerts ▶

Native Item Reorder child table + the reorder_item scheduled job — compares projected qty against reorder level daily and auto-drafts a Material Request. Zero custom code; configure reorder level/qty/warehouse per item.

OOTB STR-11 · Batch & Serial Tracking ▶

Native Serial No / Batch / Serial and Batch Bundle engine with full two-way lineage reporting. Configure naming series only.

Refine STR-12 · Expiry Management ▶

Native batch-expiry validation hard-blocks issue of expired stock. Add a Notification Rule (30-day pre-expiry alert) and one custom Script Report, Expiring Batch Alert Report.

OOTB STR-13 · Min-Max Planning ▶

Same Item Reorder engine as STR-10, extended with Min/Max levels and safety-stock buffers. Zero custom code.

Task List

One task per feature, in build order. Branch feature/scale-stock in ehiddenbrain/scale, not pushed yet. Effort is a rough T-shirt size, not a commitment.

Warehouse hierarchy

STR-03

Stock Settings & valuation method

✅ Confirmed — no work needed
Effort: Low · Depends on: Finance sign-off on valuation method (coordinate with Accounts)

Stock Entry / Receipt / Delivery configuration

✅ Confirmed working — approval workflow pending

Core purposes (Material Receipt/Issue/Transfer) confirmed working via live testing. Stock Transfer — driver/vehicle capture

2 Custom Fields (Driver Name, Vehicle Number) on Stock Entry, shown only for the Material Transfer purpose, with a "✨ New" banner + field badges. Tested live.

STR-06

Barcode / QR scan mode

Deferred
Effort: Medium · ~20 lines JS + device testing

Deliberately deferred — the source Excel itself flags this as "available polish, not a gap" (native scan_barcode already works). Lower priority than the two genuinely custom DocTypes below.

STR-07

Cycle Count Sheet (new DocType)

✅ Done
Effort: Medium · New DocType

Blind-counting DocType (Generate Items snapshots system qty hidden from the counter, Reveal Variance before submit, submit auto-creates a draft Stock Reconciliation for review). Tested live end-to-end, including a real bug caught and fixed: Float fields silently coerce an unset value to 0, so a separate is_counted flag was added to actually detect "never touched" rows before submit.

STR-08

Stock Disposition Request (new DocType + Workflow)

✅ Done
Effort: Medium · New DocType + Frappe Workflow

Stores → Finance (Accounts Manager) approval workflow; Approve auto-posts a Material Issue Stock Entry, Reject leaves stock untouched. Tested live: approve path, reject path, and a request-time validation (added after testing surfaced it) blocking a disposal quantity that exceeds actual stock.

STR-09

Reorder Alerts & Min-Max Planning

✅ Done
Effort: Low · P3, post-go-live

Reorder level/qty configured on the demo Item Reorder child table (RM-STEEL-SHEET, RM-COPPER-WIRE) against Stores - AIWS. Native engine, zero custom code — confirmed by inspecting the saved rows.

STR-10

Batch & Serial Tracking

✅ Done
Effort: Low · P3, post-go-live

Enabled batch tracking + 365-day shelf life on a demo item (CONS-LUBRICANT-OIL — has_batch_no/has_expiry_date can only be turned on before an item has any stock movement, confirmed by testing). Tested live: a Material Receipt auto-created a real Batch via the native Serial and Batch Bundle engine.

STR-11

Expiry Management

✅ Done
Effort: Low · P3, post-go-live · 1 new Script Report

30-day pre-expiry Notification (Batch, Days Before) + a new Expiring Batch Alert Report, both tested live against a real and a synthetic near-expiry batch. Caught and fixed the same class of ordering bug as PMO's CHRO Dashboard — the Workspace shortcut linked to the Report before it existed; fixed by creating dependencies before the Workspace. Also fixed after initial ship: the report was first built as a report_script-field Script Report — broken on this bench specifically (server scripts are disabled here), caught only once actually run through Frappe's real report-execution path, not just its raw SQL. Rebuilt as a standard report (real .py module), same pattern every native ERPNext report already uses.

STR-14

Rich Workspace dashboard (Number Cards, Chart, Quick Access)

✅ Done
Effort: Low — reused native records, nothing computed from scratch

The native /app/stock workspace's 3 KPI tiles (Total Stock Value, Total Warehouses, Total Active Items) and its "Warehouse wise Stock Value" chart are generic, unfiltered global records already shipped with ERPNext — confirmed directly against their query definitions before reusing them. /app/scale-stock now references the same records plus a renamed "Quick Access" shortcuts section, matching the native layout the rest of the team is used to.
