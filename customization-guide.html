The Customization Decision Framework

For every feature you need to implement, this guide tells you the right Frappe tool to use — and equally important, what not to do. This is the developer's daily reference.

The golden rule: Exhaust each level before moving to the next. A feature achievable at Level 1 (fixtures) should never be implemented at Level 3 (Python controller). The lower the level, the cheaper it is to maintain and upgrade.

How extension works — apps on the same bench

Before the 5 levels, there is a foundation concept every AIWS developer must internalize: you never copy or modify ERPNext/CRM/HRMS code. You install your custom app alongside them on the same server. Both apps share the same database. Your app only contains the differences.

The question every new developer asks: "If I create a new app for Sales or Finance, how does it get all the existing Frappe/ERPNext features?" — Answer: it doesn't need to, because both apps run on the same bench and share the same database. Frappe merges all DocTypes, hooks, and class overrides at boot time.

What you might think you need to do

  • Copy ERPNext's accounts/ folder into your app
  • Fork the erpnext repo and edit payment_entry.py
  • Duplicate the Sales Invoice DocType
  • Maintain your own branch of ERPNext

What you actually do

  • Install ERPNext and your app on the same bench
  • Add Custom Fields to ERPNext DocTypes via fixtures
  • Hook into ERPNext events via hooks.py
  • Override classes by inheriting from ERPNext originals

The 4 patterns for extending existing apps

These 4 patterns cover every scenario where you need functionality from ERPNext/CRM/HRMS inside your custom app:

Pattern 1 — Custom Fields (Level 1)

Add fields to any existing DocType without touching its source. Stored as JSON fixtures in your app, imported automatically on install.

fixtures = [
  {"dt": "Custom Field",
   "filters": [["module","=","AIWS Finance"]]}
]
# In hooks.py — fields auto-import on bench install-app

Pattern 2 — doc_events hooks (Level 2)

Intercept any lifecycle event (before_insert, validate, on_submit, on_cancel) on any existing DocType. Frappe calls your function automatically.

doc_events = {
  "Sales Invoice": {
    "on_submit": "scale_accounts.logic.compute_margin"
  }
}
# In hooks.py — no changes to Sales Invoice needed

Pattern 3 — Override class (Level 3)

Replace ERPNext's Python controller with your own subclass. Your class inherits all existing behaviour — you only override what needs to change.

override_doctype_class = {
  "Payment Entry": "scale_accounts.overrides.payment_entry.ScalePaymentEntry"
}
# Your class: class ScalePaymentEntry(PaymentEntry): ...

Pattern 4 — Link fields (Level 3)

New DocTypes in your app reference existing DocTypes via Link fields. The FK relationship gives you all ERPNext data without copying it.

{"fieldname": "supplier",
 "fieldtype": "Link",
 "options": "Supplier"}
# Pulls from ERPNext's Supplier DocType automatically

Think of it like browser extensions: Chrome already has all its built-in features. Your extension (custom app) doesn't copy Chrome's code — it hooks into Chrome's APIs and adds UI on top. When Chrome updates, your extension still works because it only uses the stable extension API, not Chrome's internals.

The 5 levels of customization

0

Configuration — no code

Roles, workflows, print formats, workspace layouts, email templates

Use when: standard ERPNext covers the business logic exactly

What you can configure without code

  • Roles & Permissions — who can read/write/submit/cancel which DocType
  • Workflows — approval chains (Draft → Pending Approval → Approved → Submitted)
  • Notification rules — email/WhatsApp alerts on doc status change
  • Print formats — invoice/quotation layouts via the Print Format builder
  • Workspaces — role-specific dashboards and quick-access links
  • Email templates — transactional email body and subject
  • Assignment rules — auto-assign leads/tickets by territory or round-robin
  • Auto-naming — naming series (e.g. AIWS-SO-.YYYY.-.#####)

How to persist config as code (fixtures)

Never rely on manual database configuration. All Level-0 config must be exported as fixtures inside your custom app so every new site gets it automatically on install.

bench — export fixtures
# In your app's hooks.py, declare what to export:
fixtures = [
  "Role",
  "Workflow",
  "Notification",
  {"dt": "Print Format", "filters": [["module", "=", "AIWS Sales"]]},
]

# Then export current site config:
bench --site mysite export-fixtures

# Files land in: apps/scale_sales/scale_sales/fixtures/
# Commit them to Git. They auto-import on: bench install-app
1

Custom Fields & Property Setters

Add fields to existing DocTypes; change field properties (label, mandatory, hidden, options)

Use when: right DocType exists but needs extra fields

Custom Fields

Add any field type (Data, Link, Currency, Table, etc.) to any existing ERPNext DocType without modifying core. The field is stored in the same MariaDB table as a new column.

Python — create via migration patch
import frappe

def execute():
  # Create a custom field on Lead DocType
  frappe.get_doc({
    "doctype": "Custom Field",
    "dt": "Lead",
    "fieldname": "bant_budget",
    "fieldtype": "Currency",
    "label": "BANT Budget",
    "insert_after": "lead_name",
    "module": "AIWS Sales"
  }).insert()
  frappe.db.commit()

Or define in JSON inside scale_sales/custom_field/lead/bant_budget.json and export as fixture.

Property Setters

Change any metadata property of an existing field: make it mandatory, hide it, change its label, add fetch-from, add options to a Select field.

Python — property setter
frappe.get_doc({
  "doctype": "Property Setter",
  "doc_type": "Customer",
  "field_name": "customer_type",
  "property": "options",
  "value": "Company\nIndividual\nDealer\nDistributor",
  "property_type": "Text"
}).insert()
frappe.db.commit()

# Always run as a patch, not interactively

Child Tables

Add a repeating row section (child table) to any existing DocType. The child table is a separate Custom DocType with a Link back to the parent.

Example: adding Competitors table to Opportunity
# 1. Create child DocType: "Opportunity Competitor"
#    fields: competitor_name, product, strength, weakness
# 2. Add Table field to Opportunity pointing to child
#    fieldname: scale_competitors, options: Opportunity Competitor
# Both done via fixtures — no manual steps on new sites
2

Server Scripts & Client Scripts

Add business logic on DocType events — validated, calculated fields, UI behaviour, automations

Use when: logic needed but no new data model required

Server Scripts (Python, runs server-side)

Scripts attached to a DocType's lifecycle events: before_insert, validate, on_submit, on_cancel, before_save, etc. Or run on a schedule (All, Daily, Weekly).

Server Script — duplicate Lead detection
# Event: "before_insert" on "Lead"
existing = frappe.db.get_all("Lead",
  filters={"mobile_no": doc.mobile_no, "status": ["!=", "Lost"]},
  limit=1
)
if existing:
  frappe.throw(
    f"Active lead already exists for {doc.mobile_no}: {existing[0].name}"
  )

Use Server Scripts for: validations, auto-calculations, sending notifications, creating linked documents, scheduling cron jobs.

Client Scripts (JavaScript, runs in browser)

Runs in the user's browser on DocType form load/change events. Used for: showing/hiding fields dynamically, auto-filling values, real-time validation messages, button actions.

Client Script — dynamic field on Opportunity
// Event: refresh on Opportunity
frappe.ui.form.on("Opportunity", {
  refresh(frm) {
    // Show probability next to stage
    frm.set_df_property("probability", "description",
      `Stage: ${frm.doc.sales_stage}`);
  },
  sales_stage(frm) {
    // Auto-set probability by stage
    const probs = {
      "Discovery": 20, "Proposal": 40,
      "Negotiation": 70, "Won": 100
    };
    frm.set_value("probability", probs[frm.doc.sales_stage] || 10);
  }
});

Important: Client Scripts are stored in the database (scriptable via bench) but should also be managed as fixtures for reproducibility.

3

Custom DocTypes with Python Controllers

New data entities with full business logic in a custom app

Use when: the gap is too large for fields+scripts; a new first-class entity is needed

When to use a Custom DocType

  • The feature needs a new list view, form view, and reports
  • It has its own lifecycle (Draft → Active → Expired)
  • Multiple other DocTypes will link to it
  • It has child tables and complex validation logic

Examples in AIWS: Dealer Profile, AMC Contract, Field Service Ticket, Content Calendar, Fleet Vehicle, Logsheet.

File structure

App structure for Custom DocType
scale_sales/
  scale_sales/
    doctype/
      dealer_profile/
        dealer_profile.json     # DocType definition
        dealer_profile.py       # Controller
        dealer_profile.js       # Client script
        dealer_profile_list.js  # List view customization
        test_dealer_profile.py  # Unit tests

Python controller pattern

Python — Custom DocType controller
import frappe
from frappe.model.document import Document

class DealerProfile(Document):
  def validate(self):
    self._validate_credit_limit()
    self._compute_scorecard()

  def on_submit(self):
    # Set as active dealer in Customer DocType
    frappe.db.set_value(
      "Customer", self.customer,
      "scale_dealer_profile", self.name
    )

  def _validate_credit_limit(self):
    if self.credit_limit < 0:
      frappe.throw("Credit limit cannot be negative")

  def _compute_scorecard(self):
    # pull last 3 months of orders + payments
    pass

Controller lifecycle hooks

Available hooks in order: before_insert → validate → before_save → after_insert / on_update → on_submit → on_cancel → on_trash

Third-party integrations

For GentooLeads, EMS, Meeting Summarizer, or any external system, write an integration module in your custom app:

Python — GentooLeads connector
import frappe, requests

def sync_gentooleads_campaigns():
  settings = frappe.get_doc("AIWS Marketing Settings")
  resp = requests.get(
    f"{settings.gentooleads_url}/api/campaigns",
    headers={"Authorization": f"Bearer {settings.get_password('api_key')}"},
    timeout=10
  )
  resp.raise_for_status()
  for campaign in resp.json()["campaigns"]:
    _upsert_campaign(campaign)

def _upsert_campaign(data):
  if not frappe.db.exists("Campaign", data["id"]):
    frappe.get_doc({"doctype": "Campaign", ...}).insert()
  else:
    frappe.db.set_value("Campaign", data["id"], ...)

Store API keys in Password type fields on a Settings DocType — never in code or env files.

What NOT to do — anti-patterns

Never do these

  • Modify any file inside apps/frappe/, apps/erpnext/, apps/hrms/, or apps/crm/ directly
  • Write raw SQL directly against the ERP database outside of frappe.db methods
  • Hardcode tenant IDs, site names, or URLs in app code
  • Use frappe.db.sql("UPDATE ...") for business logic that should be a document operation
  • Skip tests because "it's just a script" — every Server Script must have a corresponding test
  • Use frappe.flags.ignore_permissions = True without a documented reason in a comment
  • Store secrets (API keys, passwords) in Python files or environment variables — use the Password fieldtype
  • Import from one AIWS app into another AIWS app — use the public API surface (REST or frappe.get_doc)

Upgrade safety contract

These rules keep the system safely upgradeable to future ERPNext versions:

  • All custom code lives in apps under apps/scale_*/ only
  • Custom fields on standard DocTypes use a prefix: scale_ (e.g. scale_bant_budget)
  • When an ERPNext upgrade changes a standard DocType, your custom field survives because it's separate
  • Server Scripts use only public Frappe APIs (frappe.db.*, frappe.get_doc(), frappe.throw())
  • Before any ERPNext version upgrade, run the test suite on a clone of production
  • Lock the ERPNext version in apps.json / pyproject.toml — don't let it float
pyproject.toml — version pin
[tool.bench]
frappe  = "version-15"
erpnext = "version-15"
hrms    = "version-15"
crm     = "main"          # CRM uses main branch

Decision flowchart — quick reference

For any feature request, walk down this chain:

Q: "Does ERPNext already do this?"

YES — exactly as needed

→ Level 0: Configure it

Enable module, set permissions, create workflow, export as fixtures.

YES — but needs extra fields

→ Level 1: Custom Fields

Add fields via Custom Field fixture. Use scale_ prefix.

YES — but needs logic changes

→ Level 2: Server/Client Script

Hook into DocType lifecycle. Keep scripts in fixtures. Write tests.

NO — entirely new entity needed

→ Level 3: Custom DocType

New DocType + Python controller + client script in custom app. Tests required.

NO — needs a UI page, mobile app, or external integration

→ Level 4: Custom Page / API / Integration

Frappe UI page, whitelisted API, background job, or third-party connector in custom app. Full test coverage.
