1. Executive Summary & Guardrails

Today, every logged-in user of Scale PMO — Administrator, Project Manager, or a regular Employee added to a project — sees the exact same dense, uniform Frappe/ERPNext Desk. There is no role-shaped landing page, no "my work" view, and no distinction between a person who owns the whole portfolio and a person who just needs to update one task and log four hours.

This plan is not a feature push. It is a presentation-layer revamp: showing the PMO module's existing capability differently to distinct audiences (three active this round, two parked — see below), validated against how the market's most successful project tools (Asana, Monday.com, ClickUp, Linear, Basecamp, Procore) actually differentiate their own Admin / Manager / Contributor / Guest experiences. The underlying data model changes required are intentionally minimal.

Guardrails set for this track, carried through every section below:

  • Minimise DocType and structural changes — extend the existing Console/Product-Shell architecture, don’t invent a parallel one.
  • Admin keeps the current default Project form exactly as-is. The Project Manager view is where the real redesign happens.
  • Explicitly flag anywhere the plan deviates from vanilla Frappe/ERPNext conventions — see §6.
  • Five personas researched; three in active scope for this implementation round — System Admin, Project Manager, Employee (project team member). Consultant and Contractor are parked (owner decision, 2 Sep 2026) — kept in this doc for the research/analysis they already carry, revisited as a future implementation phase, not part of Phases 0–4 below.
  • Standing ET-track rule continues: build → test live → commit locally → hold every push (code and docs) until the owner explicitly says so.

2. Research — What the Market Actually Does

Direct scraping of paywalled/app-only product UIs wasn’t always possible, so research leaned on vendor documentation, comparison sites, community forums (Reddit, Asana’s own product forum), and UX-pattern write-ups (LogRocket, Eleken) alongside direct product docs. Findings are grouped by the specific question they answer.

2.1 — The three-tier Admin / Manager / Contributor split is near-universal ▸

ProWorkflow documents this explicitly: Administrators are "super users" with full settings access; Project Managers get project oversight but not account setup, and only see projects they’re assigned to manage; Team Members see only their own assigned projects/tasks, can’t run reports, and have no settings access. This exact three-way split — not two, not five — recurs across every tool researched. It directly supports the three internal personas already scoped (Admin / PM / Employee) without needing a fourth internal tier.

Sources: ProWorkflow Help Center, Asana Buyer’s Guide
2.2 — Portfolio-first landing for Managers, RAG-coloured card grids ▸

Monday.com’s dashboards consolidate multiple boards into one view specifically so managers can see "what’s stuck, who’s overloaded, what’s at risk" without opening each project — a stated 2026 industry expectation, not a nice-to-have. Portfolio-dashboard write-ups converge on the same card shape: project name, start/end date, red/amber/green status colour, and a progress bar, in a grid a manager scans in seconds. This maps almost exactly onto what the owner described independently, and onto data this app already computes (see §3 — RAG status is not new work here).

Sources: Zapier: Asana vs Monday, Teamhood: Project Portfolio Dashboard Guide
2.3 — Two speeds of task creation: quick-add vs. detailed pane ▸

Linear is repeatedly cited as faster than Asana or ClickUp specifically because actions that take 3–4 clicks elsewhere happen in a keystroke or two — a deliberate "type a title, hit enter" quick-add, with full detail (assignee, sub-tasks, custom fields, links) available but not mandatory up front. Asana's own philosophy is described the same way: "you create a task, assign it, set a date, and it shows up in the right places" — fast by default, not by removing capability. ClickUp is the counter-example: maximum control at task-creation time, at the cost of a cluttered, slower flow. This validates the owner’s instinct directly — a quick-add row above the task list, with the existing full "New Task" form still available for when detail is actually needed, rather than forcing the detailed form every time.

Sources: Linear vs Asana vs ClickUp (Medium), Gmelius: Asana vs ClickUp
2.4 — Status changes: offer drag-and-drop and an explicit control, not drag-only ▸

Drag-and-drop is the right pattern specifically when spatial position carries meaning — a Kanban board is the textbook case. But UX-pattern guidance is consistent that drag alone is the wrong choice when the list is long, dense, or better expressed as an explicit control — in those cases a status dropdown or an explicit "move to" action should sit alongside the drag gesture, not replace it. This matters directly for the Employee persona’s "My Tasks" list, which spans multiple projects and has no natural single Kanban board home — an explicit per-row status control is the correct primary mechanism there, with Kanban drag-drop staying available inside a single project’s own task board.

Sources: LogRocket: Drag-and-drop UI patterns, SaaS UI Design: Drag-and-drop patterns
2.5 — External collaborators get a hard-scoped "Guest" tier, never the internal view ▸

Asana’s Guest model is explicit: anyone outside the company email domain is a Guest by definition, sees only the specific project(s) shared with them, and is offered a binary "Can edit" / "Can comment" permission at share-time — never the full workspace. Procore’s construction-specific pattern is stricter still: merely being tagged as the "Responsible Contractor" on an item grants no automatic visibility — a contractor has to be explicitly added to a distribution list or workflow to see anything at all. Both examples independently validate a hard-scoped, opt-in visibility model for Consultant/Contractor rather than a lighter version of the internal Desk — directly relevant since this app currently has no login concept for either at all (see §3).

Sources: Asana: Guest Accounts, Procore: RFI/Submittal Permissions
2.6 — Minimalism is a legitimate, deliberate design choice for the lowest-privilege tier ▸

Basecamp’s stated philosophy is "one perfect way to work" over infinite configurability — it deliberately omits features other tools treat as standard (online/offline indicators, typing indicators, read receipts) because they conflict with the product’s async, low-noise intent. Reviews consistently describe it as "minimal yet complete," reducing onboarding time specifically because there’s nothing extra to learn. This validates the owner’s framing for the Employee persona — "not other options needed" is a defensible, researched design position for the lowest-privilege tier, not corner-cutting.

Source: ProofHub: Basecamp Review
2.7 — Timesheets: retrospective weekly grid, not a bare stopwatch ▸

Harvest’s "Week" view — fill in hours across projects for the whole week at once, editable in place — is called out as the workflow for people who log time at end-of-day or end-of-week rather than in real time, which is the realistic pattern for a project team member doing PMO admin as a secondary task. Toggl, despite being praised for the best raw UX of any time tracker, is criticised for lacking a week view at all, only a scrollable day view — a useful negative data point. This favours a weekly-grid timesheet layout for the Employee persona over a single-entry-at-a-time form.

Source: Apploye: Harvest vs Toggl comparison
2.8 — Frappe/ERPNext-native mechanics for role-based landing pages ▸

Read directly from this bench’s own frappe/website/utils.py (not just forum claims): Frappe resolves a logged-in user’s website home page through a defined chain — first Role.home_page (checked by iterating frappe.get_roles() and taking the first match), then a role_home_page hook (a dict of {role: [route]} in hooks.py), then a get_website_user_home_page method hook, then a global fallback. The community forum thread "Default Home Page route of Role" flags a real, reproducible gotcha: when a user holds multiple roles that each define a home_page, the role Frappe checks first is effectively unordered — the result is non-deterministic for any user with more than one role-based home page defined. This rules out Role.home_page as the mechanism for this plan — every real user in this system (PM, Employee) holds multiple roles. The safer levers, used below: (a) for Desk users (Admin/PM/Employee), a content-adaptive shell — one landing surface that renders different tiles based on frappe.get_roles() server-side, the same pattern the existing Product Shell already uses (see §3) — rather than a role-keyed redirect; (b) for portal/Website Users (Consultant/Contractor), the get_website_user_home_page hook is the correct, deterministic, one-hook-one-function mechanism, since it resolves per-user rather than per-role-in-arbitrary-order.

Sources: own read of apps/frappe/frappe/website/utils.py:100-165; Frappe Forum: Default Home Page route of Role; Frappe Forum: Role-Based Custom Workspace for Client

3.2 Two dashboards already exist — and neither is what’s being asked for

PMO Cockpit Dashboard (Page, role-gated to Projects Manager + PMO Director) shows aggregate portfolio metrics: Active Projects, Planned/Actual/Billed Mandays, Utilization %, Missing Logsheets. PMO Executive Dashboard (senior/exec audience) shows a similar shape one level up: Total Active Projects, On-Time Delivery %, Budget Planned vs. Actual, Resource Utilization, Task/Milestone completion, High-Risk/Delayed project counts, Timesheet Compliance, NPS.

Both are number-tile KPI pages — neither is a per-project card grid with a start date, end date, progress bar, and click-through into the project. This confirms the Phase 2 proposal below is genuinely additive, not a duplicate of what’s already built.

3.3 The extension point already exists: Scale Console + Product Shell

This bench already runs a custom chrome layer (apps/scale/scale/product_shell.py) that hides raw Frappe/ERPNext UI, replaces the Home workspace with app tiles, and gives each Scale app its own "Console" — a tab bar (Overview / Cockpit / Executive / Intelligence for Projects, defined in scale_project_management/console.py) plus labelled content sections (pos, ops, cmd, links). This is the correct place to build role-adaptive landing content — extending an existing, house-standard mechanism, not inventing a parallel one.

3.4 Things already built that this plan should reuse, not reinvent

  • Native Task view-switching (List / Kanban / Gantt / Calendar) already ships with ERPNext core, plus a custom task_list.js for this app’s Gantt/RAG rendering — "let the PM switch task views easily" is mostly a surfacing/default-view job, not new engineering.
  • pmo_rag_status / color fields, already computed on Project and Task — the exact Red/Amber/Green signal the research (§2.2) says the market uses for card grids. No new computation needed for the PM portfolio view.
  • Material Request Item.project — the native ERPNext child-row field an Employee’s "material/resource request" flow should prefill. Finding: the field lives on the child row, not the parent Material Request document — a quick-entry helper needs to write it at that level, not assume a parent-level project link exists.

3.5 Real gaps found — new ground, not a re-skin

  • Gap Consultant Profile and Contractor Profile are pure records today, with no login at all. A prospective consultant submits the public consultant-signup Web Form, a PMO Director reviews and approves the profile — and that’s the entire lifecycle. There is no User account, no portal session, nothing a consultant or contractor can log into. Giving them a real login is genuinely new surface area, not a re-skin of something that already half-exists.
  • Gap No Employee-facing minimal view exists anywhere in this app. Contrast with HR: scale_hr deliberately does not build a custom employee self-service UI — it reuses HRMS’s own native /hrms Progressive Web App for ESS/MSS (confirmed in ess_mss_demo.py), matching this project’s "never fork" convention. ERPNext Projects has no equivalent native PWA to point to, so this piece has to be genuinely built, not just wired up.
Cross-reference — 4 previously-parked PMO design gaps intersect with this work (from an earlier audit, on hold pending owner input): (2) internal approval actions like approve_timesheet are role-gated in the UI only, with no server-side check; (3) the Department Head role above has zero holders, breaking budget-approval stage 3; (4) employee-to-project assignment runs through 4 uncoupled mechanisms (Project.users, Resource Allocation, Task _assign, unguarded Timesheet.employee); (5) milestone Tasks lose their RAG colour on the Gantt bar due to a core Frappe rendering collision, not a bug in this app’s own code. Each is called out again against the specific persona section it touches below — none are silently folded into this plan’s scope without saying so.

4. Persona-by-Persona Plan

1 / 5 System Admin

Today: full raw Desk access; opens the standard ERPNext/Frappe Project form.

Proposal: keep the Project form exactly as it is today, per explicit instruction. On the existing Home/Console landing, add a small number of high-value tiles: Projects at Risk (Red RAG count), Pending Approvals across all active workflows (budget / change request / timesheet), Projects Missing a Project Manager. This mirrors §2.2’s "dashboard of dashboards" pattern — a handful of outcome tiles, not a rebuilt page.

Mechanism: extend the existing product_shell.ensure_product_home_workspace content or the Projects console tab’s pos/ops sections — additive only, no new redirect logic.

2 / 5 Project Manager

Today: same raw Desk as everyone else. The existing PMO Cockpit Dashboard (§3.2) is portfolio-wide utilization/billing metrics — useful, but not "my projects, at a glance."

Proposed landing — "My Projects" (decided, OQ1): a new tab in the existing Console tab bar (alongside Overview/Cockpit/Executive/Intelligence, defined in console.py), set as the PM's default landing. A portfolio card grid — one card per project where this user is project_manager (populated bench-wide since ET-01/ET-05) — name, start/end date, RAG colour, % progress, open/overdue task count. Click-through to the project. This is the researched, market-competitive shape from §2.2 (Monday.com-style RAG card grid), not a plain list — it's the piece of this plan that's actually meant to feel different from stock ERPNext. A small "View Cockpit →" link sits on the page for discoverability; the two views stay functionally separate (see OQ1 decision below).

Proposed project-open view (PM-specific, not Admin’s): the dense Kickoff & Governance section collapses below the fold or into its own tab; Tasks come forward with the view-switcher (List/Kanban/Gantt) prominent, plus a quick-add row above the list (§2.3 — title, optional assignee/date, one keystroke to create) sitting alongside the existing full "New Task" form for when real detail is needed.

My call: build this as a genuinely distinct, role-conditional client-script layout on the same Project/Task DocTypes (à la demo_ui.js’s existing per-field conditionals) — not a second Project form or a duplicate Page. Validated against §2.1–§2.3; the underlying schema doesn’t change.
Bundled fix — DONE, ahead of schedule (OQ5): the milestone RAG-on-Gantt bug (§3.5, item 5) was fixed and verified live this session, entirely from within scale_project_management's own task_list.js — no Frappe core file touched. Root cause confirmed in gantt_view.js: prepare_tasks() plainly overwrites a coloured task's custom_class to "bar-milestone" whenever is_milestone is set, wiping the RAG colour class before core's own set_colors() ever runs. Fix: monkey-patch GanttView.prototype.render_gantt to re-apply the correct fill to milestone bars afterward, targeting them via the native data-id attribute frappe-gantt already stamps on every bar (independent of the broken class mechanism) — a plain jQuery .css("fill", ...) on the bar/bar-progress SVG rects, no CSS-injection parsing risk. Verified live on TASK-2026-00168 (PROJ-0021, Red RAG, #dc2626): DOM inspection confirmed wrapper_class = "bar-wrapper bar-milestone" (bug reproduced) yet bar_style = "fill: rgb(220, 38, 38)" (fix applied) — and a neighbouring non-milestone task confirmed still using core's original class="color-dc2626" mechanism, untouched. Committed locally (5c416e6 on PMO_ET_phase3_role_dashboards), held from push per the standing ET-track rule.

3 / 5 Employee (project team member)

Today: more broken than it looks. It's not just that the Desk is undifferentiated — Phase 0 (§7) found the real seeded team members holding bare Employee (nothing else) have zero permission on Project and Task at all. They're listed as project team members but can't open the Project or touch their own Task today. Fixing this is Phase 4a, a hard prerequisite before any of the UI below can work.

Research validation: §2.1 and §2.6 converge tightly on the owner’s original framing — assigned work only, no reports, no settings, no visibility into anyone else’s data. This is the market-standard shape for the lowest-privilege tier, not a cut corner.

Proposed landing — "My Work": assigned Projects as cards (from Project.users where user = session user); a combined "My Tasks" list spanning all assigned projects with due date and a fast per-row status control (§2.4 — explicit control, not drag-only, since this list has no single Kanban board home); a "Log Time" shortcut; a "Request Material" shortcut.

Task status updates: a fast dropdown/segmented control per row in the flat list; Kanban drag-and-drop stays available inside a single project’s own board, per §2.4.

Material/resource request: a quick-entry that pre-fills the child-row project/task fields (§3.4 finding) and opens the native Material Request form with sensible defaults — no new DocType.

Timesheet: a weekly grid, retrospective entry against assigned tasks (§2.7) — Phase 0 needs to confirm exactly how much of this shape Frappe’s native Timesheet detail grid already supports before any new UI is built.

Explicitly excluded (validated against research, not just asserted): Budget, Risk Register, Change Requests, Reports, other employees’ timesheets, Settings.

Cut, resolved (OQ2): no "My Approvals" tile. Every approval action in this app (Budget's 5-stage chain, Timesheet approve/reject, Change Request) is role-gated to Projects Manager/Department Head/Accounts Manager/PMO Director — never to an individual or an assignee. Since the Employee persona is defined precisely as a user holding none of those roles, and the content-adaptive shell (§2.8a) routes anyone who does hold one straight to the PM landing instead, there is no state where someone sees this Employee view and has a real approval waiting — structurally impossible under the current role model, not just unlikely. A different, lighter idea sometimes meant by "delegated review" — a peer tagging a teammate to sign off on one task, Asana/ClickUp-style — doesn't exist in this app at all today (no reviewer field on Task) and would be genuinely new feature scope, not a presentation change; left as a possible separate future ET task, not bundled here. See Open Question 2.

6. Where This Does / Doesn’t Deviate from Frappe & ERPNext Core

Stays within core / reuses existing house patterns:

  • Native Task List/Kanban/Gantt/Calendar view-switcher — unmodified.
  • Native pmo_rag_status/color fields — already in schema, reused as-is.
  • Native Material Request / child-row project field — no new DocType.
  • Native Website User + get_website_user_home_page hook for the external personas.
  • has_permission / permission_query_conditions — already precedented in this app (T17/File).
  • Product Shell / Scale Console — already the house-standard chrome layer; this plan extends it, doesn’t bypass or duplicate it.

Deliberate deviation, flagged rather than hidden:

  • Vanilla ERPNext Projects has no concept of a persona-scoped "my work" landing page at all — building one is genuinely new surface area. This is the same category of deviation the Product Shell itself already represents bench-wide (hiding native chrome, replacing Home) — this plan is extending an existing, already-accepted deviation consistently, not introducing a fresh one.

Watch item — a real risk to actively avoid:

  • The PM’s revamped project-open view must not fork into a second, divergent Project form definition. Implement as role-conditional client-script rendering on the one existing form (the same technique demo_ui.js already uses per-field) — never a duplicate DocType or a parallel Page — so there is exactly one source of truth for what a Project record looks like.

7. Phase-Wise Implementation Plan

Phase 0 — Audit & Confirm (no code) DONE — 2 Sep 2026

Finding 1 — native Projects User is unusable as-is, in both directions. Read every DocPerm row shipped by ERPNext core directly: on Project and Task, Projects User is the only role with any access at all, and it's completely unscoped — full read/write/create/delete on every Project/Task in the system, no if_owner, no user-permission restriction. Confirmed against live bench data too: zero User Permission records scope Project to anyone, and only 3 accounts (2 admin/test accounts, 1 real test employee) hold the role at all — not the actual team.

Finding 2 — real team members can't see their own work today. Checked three genuine rank-and-file team members already in the seed data (Ananya Desai, Farah Khan, Karan Bhatt — role: bare Employee, nothing else, exactly this persona). Cross-referenced against the DocPerm table: Employee has zero permission on Project (an explicit read: None row) and zero permission on Task at all. They're listed in Project.users as team members but structurally cannot open that Project or touch their own Task today — a missing base grant, not a missing UI. Timesheet is fine as-is (Employee already has read/write/create there).

Finding 3 — no native weekly timesheet grid exists. Timesheet.time_logs (Timesheet Detail child table) is a flat add-a-row-at-a-time table (from_time/to_time/hours/project/task) — no day-of-week matrix UI anywhere in erpnext or hrms. Unlike the Task view-switcher or RAG fields, the §2.7 weekly-grid UX is genuinely new frontend work, not a surfacing job — flagged honestly rather than assumed as cheap as the rest of Phase 4.

Consequence for Phase 4: granting Projects User alone would fix "can't see anything" by wildly overshooting into "can see everything," directly contradicting the Employee persona's core promise (§4.3, validated in §2.1/§2.6). Correct fix, reusing a pattern already in this codebase (T17/File's has_permission + permission_query_conditions): grant Projects User to Employees who are project team members, then scope Project/Task reads/writes to rows where the session user is actually a team member — no new DocType, no schema change. Added as an explicit prerequisite step, Phase 4a below, rather than folded silently into Phase 4's UI work.
