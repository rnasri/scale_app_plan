Developer Workflow

Local environment setup, Git conventions, PR process, testing, and how multiple developers collaborate without conflict. Read this before writing any code.

Stack alignment (July 2026): This guide is aligned with the team's ehiddenbrain/scale repository. Stack: Frappe 15 · ERPNext 15 · HRMS 15 · CRM 1.x · India Compliance 15. All custom apps use the scale_* prefix. Site: scale.localhost.

Prerequisites

System requirements

  • Python 3.10–3.14 (via Homebrew — not system Python)
  • Node.js 20 LTS via nvm — CRM asset builds require Node ≥20
  • MariaDB 10.6 via Homebrew (brew install mariadb@10.6) — Homebrew now defaults to MariaDB 12+ which is incompatible with Frappe v15
  • Redis 7+ via Homebrew
  • yarn (via npm)
  • wkhtmltopdf (for PDF print formats)
  • Git 2.30+
  • Homebrew (package manager)
  • pipx (to install frappe-bench)

Setup below targets macOS (Apple Silicon / Intel). Ubuntu 22.04 is also supported — steps differ only in package manager (apt vs brew).

Git access needed

  • ehiddenbrain/scale — team collaboration repo (bench root + scale F0 app inside apps/scale/)
  • ehiddenbrain/scale_accounts
  • ehiddenbrain/scale_sales
  • ehiddenbrain/scale_supply
  • ehiddenbrain/scale_hr

Request access from the Platform lead (Ud) before starting. Custom app repos are created per module as development begins.

Knowledge required

  • Python 3 basics (classes, decorators, list comprehensions)
  • MariaDB/SQL basics
  • JavaScript/ES6 basics (for Client Scripts)
  • Git (branches, PRs, rebasing)
  • Read Frappe Capability and Customization Guide first

ERPNext experience is a plus but not required — the Customization Guide covers everything you need.

Local development setup — macOS native bench

Native bench (no Docker) gives faster hot-reload and simpler debugging. Follow these 8 phases in order. Each phase is a self-contained block — paste and run, then verify before moving on.

Node version matters. Frappe v15 + CRM requires Node 20 LTS. If you have a different Node version installed, use nvm to pin Node 20 for this project. Node 18 will cause CRM asset build failures.

Phase 1 — Install system dependencies

1a — Node 20 via nvm
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
source ~/.zshrc
nvm install 20
nvm alias default 20
node --version   # must show v20.x.x
1b — yarn
npm install -g yarn
yarn --version
1c — MariaDB 10.6 (must specify version)
brew install mariadb@10.6
brew services start mariadb@10.6
brew link mariadb@10.6 --force --overwrite
1d — Redis
brew install redis
brew services start redis
redis-cli ping   # must return PONG
1e — wkhtmltopdf + pipx + frappe-bench
brew install wkhtmltopdf pipx
pipx ensurepath
source ~/.zshrc
pipx install frappe-bench
bench --version  # confirms bench is on PATH

Phase 2 — Configure MariaDB for Frappe (utf8mb4)

Frappe requires utf8mb4 charset. Edit the config file once, then restart.

/opt/homebrew/etc/my.cnf
[mysqld]
character-set-client-handshake = FALSE
character-set-server = utf8mb4
collation-server = utf8mb4_unicode_ci
innodb_file_per_table = 1

[mysql]
default-character-set = utf8mb4
Restart and verify
brew services restart mariadb@10.6
mariadb -u root -e \
  "SHOW VARIABLES LIKE 'character_set_server';"
# must show: utf8mb4

Phase 3 — Set MariaDB root password

Fresh Homebrew MariaDB 10.6 uses socket auth — sudo mariadb -u root won't work. Connect as your system user instead:

bash — set root password to "admin" (dev only)
# Connect as your macOS system user (no password needed on fresh install)
mariadb -u $(whoami) -e \
  "ALTER USER 'root'@'localhost' IDENTIFIED BY 'admin'; FLUSH PRIVILEGES;"

# Verify root login with password:
mariadb -u root -padmin -e "SELECT 1;"

Phase 3b — MariaDB GUI (optional but recommended)

A GUI client makes it easy to browse Frappe's tables, inspect DocType data, and debug queries during development. Two free options:

Sequel Ace — recommended

Free, macOS-native, lightweight. Best for everyday table browsing and quick queries. Active fork of Sequel Pro.

Install: Search Sequel Ace on the Mac App Store (free).

Connection settings:

Sequel Ace — connection
Host:     127.0.0.1
Port:     3306
Username: root
Password: admin
Database: scale_localhost

Use Standard connection type. Leave SSL unchecked for local dev.

DBeaver Community

Completely free, open source. Heavier (Java-based) but more powerful: ER diagrams, schema comparison, data export, full query editor with autocomplete.

Install:

bash
brew install --cask dbeaver-community

Connection settings:

DBeaver — new connection
Driver:   MariaDB
Host:     localhost
Port:     3306
User:     root
Password: admin
Database: scale_localhost

Choose MariaDB driver (not MySQL) when prompted. DBeaver will offer to download the driver automatically.

Useful Frappe tables to know: tabDocType (all DocTypes), tabCustom Field (your custom fields), tabSingles (single-record configs), tabGL Entry (accounting ledger). Every Frappe DocType becomes a tab<DocType Name> table.

Phase 4 — Initialize the bench

This clones Frappe v15 and installs all Python dependencies. Takes 3–5 minutes.

bash — bench init
cd ~
bench init scale-bench --frappe-branch version-15
cd scale-bench
export NVM_DIR="$HOME/.nvm" && . "$NVM_DIR/nvm.sh" && nvm use 20

Phase 5 — Get all Frappe apps

Use the pinned versions that the team has tested and committed to sites/apps.json.

bash — install ERPNext, HRMS, CRM, India Compliance
bench get-app erpnext --branch version-15
# Pinned: ERPNext 15.118.1 (commit b9c9b76)

bench get-app hrms --branch version-15
# Pinned: HRMS 15.63.1 (commit c0ab60b)

bench get-app crm
# CRM uses main branch — v1.79.1 (commit 0e6e651)

bench get-app https://github.com/resilient-tech/india-compliance --branch version-15
# Pinned: India Compliance 15.30.4 (commit 3fea732) — must use full URL, not on frappe org

Pinned versions matter. The team has validated this exact combination. If you pull later commits from upstream and something breaks, check sites/apps.json in the ehiddenbrain/scale repo for the team's tested pinned hashes.

Phase 6 — Create site and install apps

Homebrew MariaDB 10.6 uses a Unix socket at /tmp/mysql.sock — pass the socket flag explicitly.

bash — new site
bench new-site scale.localhost \
  --mariadb-root-password admin \
  --admin-password scale@demo \
  --mariadb-db-socket /tmp/mysql.sock

bench --site scale.localhost install-app erpnext
bench --site scale.localhost install-app hrms
bench --site scale.localhost install-app crm
bench --site scale.localhost install-app india_compliance
bench --site scale.localhost install-app scale

Hostname routing: Frappe matches requests by hostname. Add scale.localhost to /etc/hosts so the browser can reach it:

echo "127.0.0.1 scale.localhost" | sudo tee -a /etc/hosts

Phase 7 — Enable developer mode and start

bash — developer mode + start bench
bench --site scale.localhost set-config developer_mode 1
bench set-config -g developer_mode 1
bench use scale.localhost
bench start

Open http://scale.localhost:8001 — login: Administrator / scale@demo

Phase 8 — Install the scale app

The scale app (F0 foundation) is already in the repo at apps/scale/. You do not need to run bench new-app — just install it and run migrations:

bash — install scale app from repo
# The repo was cloned into the bench root, so apps/scale/ is already present.
# Install it into pip and register it with the site:
bench --site scale.localhost install-app scale
bench --site scale.localhost migrate

Why migrate? The scale app adds custom fields to the Customer DocType via install.py. Running migrate ensures those fields are applied and any fixture data is loaded.

F0 gate — bench is ready when: http://scale.localhost:8001 loads, ERPNext Selling module is enabled, you can create a Lead and a Sales Invoice end-to-end, the Customer form shows Scale Priority and Scale Account Notes fields, and a second developer can spin up the same bench from scratch using only these instructions.

Creating a new custom app (for each module team)

Each team (Accounts, Sales, HR, Supply) owns one custom app. All customizations — DocTypes, hooks, fixtures, API functions — live inside that app. Never modify apps/erpnext, apps/frappe, or any other upstream app.

bash — scaffold a new Scale app
# From inside the bench directory:
bench new-app scale_sales
# Prompts: App Title = "Scale Sales", Publisher = "Pixaflip Technologies"
# Creates: apps/scale_sales/ with the standard Frappe app structure

# App structure created:
scale_sales/
  scale_sales/
    __init__.py
    hooks.py           # ← register all hooks here
    modules.txt        # ← list module names
    patches.txt        # ← list patch scripts in order
    config/
      desktop.py       # ← workspace shortcuts
    public/            # ← static assets (JS, CSS, images)
    templates/         # ← Jinja templates for web pages
    scale_sales/       # ← module folder (matches module name)
      doctype/         # ← Custom DocTypes go here
      report/          # ← Script Reports go here
      page/            # ← Custom pages go here
      fixtures/        # ← Exported fixtures (JSON) go here
      tasks.py         # ← Scheduled job functions
      api.py           # ← Whitelisted API functions
  setup.py
  requirements.txt     # ← third-party pip dependencies
  pyproject.toml       # ← version and bench version pins

Custom field naming convention: always prefix fields with scale_<team>_<name> (e.g. scale_acc_credit_limit, scale_sales_bant_score). This avoids clashes across apps and makes fixture filters precise.

Git workflow — branches and PRs

BranchPurposeWho pushesProtection
main Production-ready code. Deployed to staging on every merge. No direct push — PRs only Require PR review + CI green
develop Integration branch. All feature branches merge here first. PRs from feature branches CI must pass
feature/accounts-credit-limit One feature or bug fix. Named with team and topic. Assigned developer None
fix/hr-leave-approval-npe Urgent production fix. Merges to both main and develop. Assigned developer Extra reviewer required

Day-to-day feature workflow

  1. 1

    Pull latest develop

    git checkout develop && git pull

  2. 2

    Create feature branch

    git checkout -b feature/sales-dealer-scorecard

  3. 3

    Develop and commit incrementally

    Small, focused commits. Commit message: feat(sales): add dealer scorecard aggregation

  4. 4

    Export fixtures before PR

    bench --site scale.localhost export-fixtures --app scale_sales

  5. 5

    Run tests locally

    bench --site scale.localhost run-tests --app scale_sales

  6. 6

    Open PR against develop

    Link the ticket. Tag the module owner as reviewer.

Commit message convention

Use the Conventional Commits format:

Format
<type>(<scope>): <description>

Types:
  feat     - new feature
  fix      - bug fix
  refactor - code change, no feature/fix
  test     - adding tests
  docs     - documentation
  chore    - build/config changes
  fixture  - fixture export update

Scopes: sales, accounts, supply, hr, core, pmo

Examples:
feat(sales): add BANT scoring fields to Lead DocType
fix(accounts): correct GST credit check validation
fixture(sales): export updated Dealer Profile DocType
chore/accounts-fixtures-gst-fields

PR checklist (required before review)

  • Changes only in the correct custom app (no edits to upstream apps)
  • Fixtures exported and committed
  • Tests written and passing locally
  • bench --site scale.localhost migrate runs clean
  • No frappe.flags.ignore_permissions without comment
  • No hardcoded site names, URLs, or credentials in code
  • Patch added if a DB schema change is included
  • Module owner tagged as reviewer

Handling fixture conflicts — the #1 multi-developer pain point

Fixtures are JSON files. Two developers modifying the same DocType's custom fields will create Git conflicts in the fixture JSON. This is the most common source of friction in Frappe multi-developer projects. The rules below prevent it.

Rules to avoid fixture conflicts

  • Each module app owns its own fixtures. Never put scale_sales fixtures inside scale.
  • One developer per DocType at a time. Co-ordinate via the ticket board — assign ownership clearly.
  • If two developers must work on the same DocType simultaneously, work on different fields, then one person does a final fixture export after both are done.
  • Always pull develop and run bench --site scale.localhost migrate before starting work on fixtures.
  • Never manually edit fixture JSON — always go through the Frappe UI and then export.
  • Shared DocTypes (Customer, Item, Company): prefix all custom fields with scale_<team>_ and coordinate in PR description.

When a fixture conflict happens

  1. Do NOT auto-resolve the Git conflict with <<< markers — the JSON will be invalid.
  2. Accept one version completely (git checkout --theirs or --ours).
  3. On your local site, manually re-apply the changes from the discarded version via the Frappe UI.
  4. Re-export fixtures: bench --site scale.localhost export-fixtures --app scale_sales
  5. Commit the merged fixture JSON.

This is why step 4 of the feature workflow (export fixtures) must be the last step before opening a PR — minimizes the window for conflicts.

Testing

Running tests

bash — run tests
# Run all tests for an app
bench --site scale.localhost run-tests --app scale_sales

# Run tests for a specific module
bench --site scale.localhost run-tests \
  --module scale_sales.scale_sales.doctype.dealer_profile.test_dealer_profile

# Run with verbose output
bench --site scale.localhost run-tests --app scale_sales -v

Writing a test

Python — test template
import frappe
import unittest

class TestDealerProfile(unittest.TestCase):
  def setUp(self):
    # Create test data
    self.customer = frappe.get_doc({
      "doctype": "Customer",
      "customer_name": "Test Dealer Ltd"
    }).insert()

  def test_negative_credit_limit_rejected(self):
    with self.assertRaises(frappe.ValidationError):
      frappe.get_doc({
        "doctype": "Dealer Profile",
        "customer": self.customer.name,
        "credit_limit": -1000
      }).insert()

  def tearDown(self):
    frappe.db.rollback()

Testing philosophy

  • All new DocType controllers require unit tests covering: validation errors, happy path, edge cases.
  • Server Scripts require at least one test covering the event they hook.
  • API functions require permission tests (unauthenticated call should fail).
  • Integration connectors (GentooLeads, EMS) require mocked HTTP tests.
  • Coverage target: 70% for new DocTypes, 80% for API functions.

CI pipeline (GitHub Actions)

.github/workflows/test.yml (skeleton)
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-22.04
    services:
      mariadb: { image: mariadb:10.6, ... }
      redis:   { image: redis:7-alpine }
    steps:
      - uses: actions/checkout@v4
      - name: Set up Frappe bench
        uses: frappe/frappe-bench-action@main
        with:
          frappe-branch: version-15
          apps-json: apps.json
      - name: Run tests
        run: bench --site test.localhost run-tests --app scale_sales
