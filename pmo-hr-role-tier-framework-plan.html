1. Purpose & the Problem Being Solved

Scale is being built by extending Frappe/ERPNext, not replacing it — every module (PMO, HR, Sales, Purchase, Stock, Manufacturing, Accounts, Finance) sits on top of native DocTypes, Roles, and Permissions rather than a parallel system. ET Phase 3 (see pmo-phase3-role-dashboards-plan.html) took the first real step toward role-shaped logins in PMO: a Project Manager gets a "My Projects" portfolio landing, a plain team member gets a personal "My Work" hub, and both are gated by a hardcoded two-way split in the code (elevated roles vs. everyone else).

The next problem is different in kind, not just degree: Scale will be sold to multiple client organizations, and each one has its own org chart, its own job titles, and its own number of management layers. One client's "Site Engineer" and another's "Software Developer" are the same access tier — an individual contributor doing assigned work — but nothing in the system today expresses that. Today, "who sees what" is decided by literal Frappe Role names (Projects Manager, PMO Director, Department Head — see §4) written directly into Python and JavaScript. Onboarding a new client today would mean either forcing their org onto our exact role names, or editing code per client — neither scales.

This document's job is to lay a solid, research-grounded foundation before any of that gets built: understand exactly what Frappe/ERPNext already gives us for free, audit exactly what this codebase has already built, research how other systems solve the same class of problem, and only then propose a framework — generic enough to onboard any client's hierarchy, concrete enough to actually implement.

2. The Core Idea: Two Orthogonal Axes

The single most important design decision in this document is recognizing that "role" in the owner's brief is really two separate questions that Frappe already answers very differently:

Axis 1 — Functional Role
"What can you DO?"

Can you create a Task? Approve a Purchase Order? See a Salary Slip? This is native Frappe Role / DocType Permission / Workflow territory — Projects Manager, Purchase Manager, HR Manager, Accounts Manager are all functional roles. This machinery already works well in this codebase (team_scope_hooks.py, the PUR-01 workflow, custom_docperm.json) and does not need to be reinvented.

Axis 2 — Organizational Tier
"Whose data can you SEE, and what dashboard do you land on?"

Are you an individual contributor, a first-line supervisor, a department manager, or a board member? This is a presentation and visibility-scoping layer — it decides which dashboard you land on and how far down the org chart your view reaches. This axis barely exists in the system today — it's currently a single hardcoded boolean (elevated vs. not) baked into JS/Python. This is the actual gap this document addresses.

Salesforce's own documentation for its (much more mature) equivalent system states the same split in one line worth borrowing directly: "Roles see, profiles do." Applied here: functional Role decides what you can do; Org Tier decides what you can see and where you land. The framework below only touches the second axis — it is additive on top of the first, not a replacement for it.

Source: DESelect — Salesforce Role Hierarchy Explained

3. Frappe/ERPNext's Native Role & User Mechanism — What Actually Exists

Before proposing anything new, here is exactly what Frappe/ERPNext already ships, confirmed against this bench's own installed frappe/erpnext/hrms source and live data, not just documentation:

3.1 Role, Has Role, and DocType Permissions

A Role is a named permission bucket (Projects Manager, HR User, etc.). A DocPerm row (native, or a Custom DocPerm for standard doctypes we don't own — the distinction ET Phase 3 hit a real bug over, see §4.3) grants a Role read/write/create/delete/submit rights on a DocType, optionally at a permission level (permlevel) for field-by-field gating (used for the anonymous-360-feedback fix on PR #43). A User gets Roles via the Has Role child table on the User doctype — frappe.get_roles(user) is the runtime check used everywhere in this codebase (team_scope_hooks.py, library_hooks.py, tab_visibility.js's frappe.user_roles).

3.2 Role Profile — a static bundle, not a hierarchy

A Role Profile bundles several Roles into one named template, assignable to a User in one field — meant for fast onboarding ("assign the Sales Role Profile" instead of 4 separate Roles). Confirmed live on this bench: 6 Role Profiles exist (HR, Purchase, Sales, Accounts, Manufacturing, Inventory) — none for PMO, and none express any notion of seniority or tier. Official docs confirm this is by design: Role Profiles are static, fixed lists with no conditional or tiered logic — they cannot themselves express "this bundle means Tier 3, that one means Tier 5." Useful as an assignment convenience, not as the hierarchy mechanism itself.

Source: Frappe Docs — Role and Role Profile

3.3 Designation and Department — the org-chart vocabulary, mostly unused as one

Designation is a free-text-ish master list (job titles) linked from Employee — not company-scoped natively (confirmed: no company field on the Designation doctype), so it's a single global vocabulary per bench/deployment. Department is a genuine Frappe NestedSet tree doctype (parent/child departments, same tree mechanism as Item Group or Territory) — capable of real multi-level org structure, but see §4.2 for how it's actually being used on this bench today (not much).

3.4 Employee.reports_to — a real NestedSet tree, not just a display field

Key finding, verified directly against the installed erpnext source (erpnext/setup/doctype/employee/employee.py): the Employee doctype's own controller declares nsm_parent_field = "reports_to" — meaning Employee is already a bona fide Frappe NestedSet tree, keyed on reports_to, the exact same mechanism Department/Item Group/Territory use. Confirmed live on this bench too (frappe.get_meta("Employee").is_tree == True). This means Frappe's own tree utilities — frappe.utils.nestedset.get_descendants_of("Employee", X), get_ancestors_of() — already return "everyone under this person in the reporting chain" today, for free, using the exact lft/rgt machinery Frappe maintains automatically whenever reports_to is set or changed. Nothing needs to be built to get this query capability — it already exists.

What's not automatic: wiring that tree into actual permission enforcement (deciding who can see a subordinate's Task/Timesheet/Leave Application). Frappe HR's own documentation describes a "restrict by hierarchy" pattern for Leave Application/Expense Claim/Appraisal built on top of exactly this field — but reading the actual controllers (leave_application.py, expense_claim.py) shows they gate through frappe.has_permission("Employee", "read", employee) rather than a fully automatic out-of-the-box hierarchy grant. In other words: the tree is native and free; the permission-enforcement hook on top of it is the same category of work this codebase has already done three times — library_hooks.py (File, scoped to Project Library tagging), team_scope_hooks.py (Project/Task, scoped to Project team membership). A fourth hook, scoped to the reports_to tree instead of flat team membership, is the same pattern applied to a new axis — not new technique.

Sources: Frappe HR Docs — User Permission Based on Hierarchy, frappe/utils/nestedset.py (GitHub), and this bench's own apps/erpnext/erpnext/setup/doctype/employee/employee.py

3.5 has_permission / permission_query_conditions — the actual enforcement mechanism this codebase already uses

Every real access-scoping feature in Scale so far — File visibility (T17), Project/Task team-scoping (ET Phase 3 Phase 4a) — uses the same native Frappe hook pair: a controller-level has_permission(doc, user) function (checked on direct document access) plus a matching get_permission_query_conditions(user) function (a raw SQL fragment injected into every list/report query for that doctype). Both are registered per-doctype in hooks.py. This is the mechanism the proposed framework's own tier-scoping will reuse — not a new concept for this codebase, the fourth application of one already proven three times.

3.6 Workflow — functional approval chains, a separate concern

Multi-stage approval (e.g. the live Purchase Requisition Approval Workflow on Material Request — Draft → Department Head → Purchase Manager → Accounts Manager → [Purchase Master Manager if high-value] → Approved) is native Frappe Workflow, gated per-state by functional Role names. This is squarely Axis 1 (functional role, "who is allowed to approve a purchase") — the framework below deliberately does not touch it; see §7's explicit statement on why Tier and approval-authority Role must stay decoupled.

4. Current-State Audit — Grounded in Live Data

All figures below were queried directly against scale.localhost during this session, not estimated.

4.1 Designations already contain almost exactly the ladder the owner described

48 Designations exist on this bench today, including: Trainee, Executive Trainee, Management Trainee, Executive, Sr. Executive, Asst Manager, Deputy Manager, Manager, Sr. Manager, General Manager, Director, Vice President, Managing Director, President, plus C-suite (CEO/CFO/COO/CTO) — alongside sector-specific individual-contributor titles like Software Developer, QA Engineer, DevOps Engineer, Business Analyst, Engineer, Designer. This confirms the exact shape of the problem the owner described: Designation is already the "client/sector-specific title" vocabulary (a "Site Engineer" and a "Software Developer" are both real, different Designations) — what's missing is a layer above it that says both of those map to the same generic tier.

4.2 Department and reports_to are present but functionally unused as a hierarchy

Every real Department on this bench (Accounts, Sales, Purchase, Operations, Production, HR, Management, etc.) is a direct child of "All Departments" — zero actual nesting, despite Department being a genuine tree doctype capable of it. More significantly: only 3 of 23 real Employees have reports_to set at all. The single native field that would make the NestedSet tree in §3.4 actually meaningful is almost entirely unpopulated. This is not a missing feature — it's missing data entry, which is itself a finding: any tier/hierarchy framework must include a real backfill step (reusing the exact "auto-backfill via demo_setup.run_et_phase3_role_scope_backfill"-style idempotent script pattern already used twice in this codebase), not assume the data is already clean.

4.3 PMO's current access model is a hardcoded binary, not a tier ladder

Read directly from team_scope_hooks.py (live on this bench):

ELEVATED_ROLES = {"System Manager", "PMO Director", "Projects Manager"}

def has_permission_project(doc, user=None, permission_type=None):
    if _is_elevated(user):
        return True
    return bool(frappe.db.exists("Project User", {"parent": doc.name, ...}))

The exact same ELEVATED_ROLES set, independently hardcoded a second time, drives which Console tabs render at all (tab_visibility.js). There is no middle ground: a user is either fully elevated (sees every Project/Task bench-wide, gets the full tab bar) or scoped to only Projects where they personally have a Project User row (sees just their own assigned work). There is no "supervisor of a team" state today — exactly the gap the owner named directly ("a supervisor and manager can approve things for their team below, and can see only that what is relevant").

Real, currently-live gap: the code review of refactor/project-module (this session, see prior conversation) found this same hardcoded pattern independently reimplemented with slightly different role lists in at least 4 separate files (pmo_home.js, pmo_my_projects.js, task_list.js, scale_app_sidebar.js). This is exactly the kind of drift a single, data-driven Tier resolution (§7) eliminates by construction — one source of truth instead of four hand-copied lists.

Because both PMO and HR ultimately key off the same Employee record and the same (currently unpopulated) reports_to chain, an Org Tier resolved once per Employee (§7) is naturally shareable across both apps — this is the concrete mechanism behind the owner's "combined login for employees" ask, addressed directly in §9.4.

5. External Research — How Comparable Platforms Solve This

5.1 — "Roles see, profiles do": the dual-axis pattern is a proven enterprise model ▸

Salesforce — the most mature real-world analog to what's being proposed — separates its access model into exactly the two axes in §2. Role Hierarchy is a vertical structure controlling record-level visibility only (a VP can see records owned by a Sales Manager beneath them in the hierarchy) — roles never grant edit rights, they only "open your eyes." Profiles (plus Permission Sets layered on top) control what actions are actually possible — object/field permissions, create/edit/delete. The two are deliberately orthogonal and independently assignable per user. This validates §2's framing directly: it is not a novel idea to keep "who can see how far up/down the org chart" separate from "what actions can this person perform" — it is how the industry's most-copied enterprise permission model already works.

Sources: DESelect: Salesforce Role Hierarchy Explained, DESelect: Roles vs Profiles vs Permission Sets (2026)
5.2 — Job Level vs. Job Title: the exact abstraction the owner is asking for, already solved in HR theory ▸

Modern job-architecture practice draws a hard line between Job Title (what's on the business card — company- and even team-specific) and Job Level (the generic rung on a shared ladder that defines expectations and access, independent of title). The standard failure mode named directly in this research is "title inflation" across companies of different sizes — a "Director" at a 50-person company and a "Senior Manager" at a large enterprise can sit at the same real level despite very different titles. The recommended fix (three tests: interchangeability, market comparability, organizational equivalence) is exactly the exercise the owner described doing manually per client ("map it for the client from executive to their lowest level"). This is strong external validation that a fixed, generic Level/Tier ladder with a per-client title-to-level mapping is the correct, well-established shape for this problem — not something being invented from scratch.

Sources: Deel: Job Level Classification, Native Teams: Job Level Classification Frameworks
5.3 — Frappe/ERPNext's own community pattern for per-branch/per-unit role variants ▸

Community guidance for multi-unit ERPNext deployments (e.g. "HR Manager – Mumbai Branch") shows the common workaround today is duplicating Roles per branch/company — a real Role explosion problem, and precisely the failure mode a generic Tier + per-client mapping table is meant to avoid (one small mapping table per client instead of N duplicated Roles). This is useful negative evidence: it shows the naive native-only approach (just make more Roles) is a known anti-pattern in this exact ecosystem, reinforcing that a mapping layer above Role/Role Profile is the right additional piece, not redundant with what already exists.

Source: Frappe Academy — Mastering User Roles and Permissions in ERPNext

6. Why Today's Model Won't Scale Across Clients

  • Role names are destiny, and they're hardcoded in ≥5 places. ELEVATED_ROLES appears independently in team_scope_hooks.py, library_hooks.py, tab_visibility.js, plus (per the recent code review) 3 more re-implementations on refactor/project-module alone. Onboarding a client whose hierarchy doesn't map cleanly onto exactly "Projects Manager vs. everyone else" means editing code, not configuration.
  • There is no middle tier — Phase 0's own audit (§4.4, and the original ET Phase 3 research) already found this: a real Supervisor/Team-Lead persona ("sees and monitors everything for their owned team, approves for them, nothing portfolio-wide") does not exist in the code at all today.
  • No mechanism ties a client's own vocabulary to our access model. Designation is rich (§4.1) but purely descriptive — nothing reads it to decide dashboard/visibility.
  • The one native mechanism built for exactly this (reports_to's NestedSet tree, §3.4) is unpopulated (§4.2) — the foundation exists, the data doesn't.

7. Proposed Framework: the Scale Org Tier System

A small, additive layer on top of everything in §3 — no existing Role, Workflow, or DocPerm is replaced.

7.1 The generic tier ladder (default reference set, refinable per client)

Nine tiers, directly following the ladder the owner named, treated as a reference default — a client with a flatter org (say, no AVP layer) simply doesn't populate that tier's mapping; the mechanism doesn't require exactly nine.

1 Executive — Individual Contributor / Doer

Does assigned work, no one reports to them. Client-specific titles map here: Developer, Software Engineer, Site Engineer, QA Engineer, Executive, Trainee, etc. Already built — today's "My Work" persona.

2 Senior Executive / Supervisor

Still does own work, but a small number of Tier-1 people report to them directly. Sees/monitors their direct reports' work, can approve for them. Genuinely new persona — see §9.1.

3 Assistant Manager

Manages one or more Supervisors' teams; approval authority widens; still largely operational, not strategic.

4 Manager

Owns whole Projects/Departments end to end. Closest existing match: today's "My Projects" persona — generalizing its gate from a flat role-list to Tier 4+reports_to-scope is most of the work here.

5 Senior Manager

Cross-project/cross-team oversight within a function; first tier where reporting/analytics start to outweigh task-level detail.

6 AVP

Multi-department/business-unit view; approval authority for higher-value items (mirrors the existing value-threshold pattern already in the PUR-01 workflow, applied as a concept, not shared code).

7 VP

Org-wide operational dashboards; still a real decision-maker on escalations, but drill-down into individual task minutiae is no longer the point.

8 President / C-Suite

Per the owner's own framing: administrative, reporting, and decision-facing dashboards only — explicitly not project/task-level detail. Reuses/extends the existing PMO Executive Dashboard, with drill-down links removed rather than added.

9 Board of Directors

Least operational detail of all — quarterly/portfolio-level strategic summaries. Candidate for a lighter Portal-type login rather than full Desk access (see Open Question 3, §11).

7.2 The mapping mechanism (this is the actual new piece)

  1. New doctype: Scale Org Tier — a small master list (our 9 generic tiers above, seeded once), global to the deployment.
  2. New doctype: Scale Designation Tier Map — one row per Designation → Scale Org Tier (e.g. Software Developer → Tier 1, Site Engineer → Tier 1, Project Manager → Tier 4). This is the literal admin screen the owner described: at client onboarding, someone walks the client's real Designation list once and assigns each a Tier. A single grid-style list view is enough — no custom UI needed beyond what Frappe's own List View already provides.
  3. Employee gets one new fetched field, scale_org_tier (Link → Scale Org Tier), auto-computed from the Employee's designation via the mapping above. Same "computed field, set via an on_update/validate hook plus a one-time idempotent backfill script" pattern already used three times in this codebase (ET-01's Manager Name, ET-02's top_skill, ET Phase 3's own role/scope backfill) — no new technique.
  4. New hook module, org_tier_hooks.py — exposes get_my_tier(user) and get_my_team_employees(user) (the latter a thin wrapper over frappe.utils.nestedset.get_descendants_of("Employee", employee_id), §3.4 — restricted to Active employees, elevated-role bypass using the exact same pattern as team_scope_hooks.py's _is_elevated()). This is the one new has_permission/permission_query_conditions pair proposed — the fourth application of a pattern this codebase has already built three times (§3.5).
  5. Dashboard/tab routing reads Tier from boot info (exposed once via frappe.boot.scale_org_tier, computed server-side at login), replacing every hardcoded ELEVATED_ROLES array (§4.3, §6) with one if (tier >= X) check sourced from one place.
Deliberately not touched: Workflow-driven functional approval chains (PUR-01's Material Request states, etc.) keep using named functional Roles exactly as today. Tier is a visibility/presentation concept; "who is allowed to approve a Purchase Order" stays a Role/Workflow concept, per §2's axis split. Conflating the two — e.g. auto-granting "Purchase Manager" just because someone is Tier 4 — would silently grant real transactional authority to anyone who happens to be a Tier-4 manager in an unrelated function, which is exactly the kind of scope-creep this framework should prevent, not cause.

9. How This Maps onto What's Already Built

9.1 The genuinely new persona: Supervisor (Tier 2/3)

This does not exist in any form today. It reuses the "My Projects" card-grid/RAG UI pattern (already built, already proven) but scopes the underlying query to "my reports_to subtree's assigned Tasks/Timesheets" instead of "Projects where I'm the named PM" — a query-shape change, not a new UI paradigm.

9.2 Manager (Tier 4) — generalize, don't rebuild

"My Projects" already does almost everything Tier 4 needs. The work here is replacing its ELEVATED_ROLES gate with a Tier check, so a client who calls this role "Delivery Head" instead of "Project Manager" still lands here correctly once their Designation is mapped.

9.3 Top tiers (7–9) — subtract, don't add

The existing PMO Executive Dashboard is already close to the President/VP shape described by the owner (administrative, decision-facing, no task-level noise). The work for these tiers is largely about removing drill-down links a Tier 4 Manager should have and a Tier 8 President should not, not building new widgets.

9.4 The "combined employee login" ask — PMO + HR + internal Scale, one Tier-1 hub

Because scale_org_tier would live on the shared native Employee record (not inside any one app), it is naturally visible to every app that reads that Employee — PMO, HR, and the separate internal "Scale" app alike. A single aggregator "My Work" hub (a new thin page, likely in the mother scale app rather than duplicated per-module) can call each already-installed app's own existing whitelisted "get my stuff" method — scale_project_management.my_work_hooks's pattern already exists; HR/Scale would need an equivalent, small, per-app method — and merge results into one combined view. This is additive aggregation, not a merger of the underlying apps, and is flagged as its own later phase (§10, Phase 6) rather than something to force into the PMO-only Phase 1–5 work.

10. Phased Implementation Plan

Phase 1 — Foundation doctypes & data

Build Scale Org Tier + Scale Designation Tier Map, add Employee.scale_org_tier, write the backfill script, populate reports_to for this bench's own 23 real Employees (§4.2) as the reference dataset. No UI changes yet.

Phase 2 — org_tier_hooks.py, the fourth scoping hook

Build get_my_tier()/get_my_team_employees(), wire into frappe.boot. No visible UI change yet — purely plumbing, testable via console.

Phase 3 — Collapse the hardcoded role lists

Replace every ELEVATED_ROLES/tab-visibility hardcode (§4.3, including the 3 extra copies found on refactor/project-module) with a single Tier-driven check sourced from boot info. Zero visible behavior change if done correctly — a pure refactor, verified by confirming today's users land on exactly the same pages as before.

Phase 4 — New Supervisor (Tier 2/3) persona

The one genuinely new dashboard — "My Team" hub, reusing the My Projects card-grid pattern scoped to reports_to descendants instead of PM'd Projects.

Phase 5 — Top-tier dashboards (7–9)

Extend/gate the existing Executive Dashboard per tier; design the Board of Directors' lighter-weight (possibly Portal) login.

Phase 6 — HR parity + combined "My Work" (separate document)

A dedicated HR-focused follow-up to this document, applying the same Tier framework to scale_hr, plus the cross-app aggregator hub from §9.4.

2
Supervisor scope depth. Should Tier 2 see only direct reports, or their full reports_to subtree (matters once a Supervisor has other Supervisors under them)?

5
Sequencing vs. Muhammad's refactor/project-module fork. That branch reimplements the elevated-role check independently in 4 places (§4.3) — should Phase 3's collapse happen before or after that branch is reviewed/merged, to avoid collapsing a version of the logic that's about to be replaced anyway?
