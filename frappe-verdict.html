Frappe / ERPNext Capability Assessment

What the Frappe ecosystem gives us out-of-the-box, what needs extension, and what must be built — per module.

The 5 Frappe concepts every developer must know

DocType

The fundamental Frappe building block. A DocType is simultaneously a database table definition, a web form, and a REST endpoint. Define a DocType and Frappe creates the DB table, generates CRUD APIs, and renders the form — automatically.

There are two kinds relevant to us: Standard DocTypes (from ERPNext core, never modify) and Custom DocTypes (our additions, live in custom apps).

App & Bench & Site

Bench = the server installation (Python env + apps + config). App = a Python package installed on the bench (ERPNext is one app; our custom modules are separate apps). Site = one tenant — has its own MariaDB database, its own config, and can have a subset of apps installed.

One bench can host hundreds of sites. All sites share the same app code but are completely isolated in data.

Hooks

The integration contract between apps. Hooks (in hooks.py) let your custom app intercept Frappe framework events without touching any core code: doc_events (DocType lifecycle), scheduler_events (cron jobs), on_login, after_install, etc.

Hooks are how you extend ERPNext without forking it. This is the correct pattern — always.

Fixtures

JSON exports of configuration (Custom Fields, Property Setters, Roles, Workflows, Print Formats, etc.) that live inside your app and are auto-imported on install. Fixtures make your configuration reproducible and version-controlled — the only way to manage config in a team.

Running bench export-fixtures captures current config. Running bench --site mysite install-app myapp restores it.

Patches

Python scripts that run once per site during an upgrade to migrate data or repair state. Example: renaming a field, backfilling a new column, or migrating old records to a new DocType. Patches are tracked in patches.txt — Frappe ensures each patch runs exactly once per site.

Never write ad-hoc migration scripts. Always use patches.

Frappe UI vs. Frappe Desk

Frappe Desk (the existing ERPNext UI) is a mature, full-featured interface that auto-generates list views, form views, and dashboards from DocTypes. Frappe UI is a newer Vue.js component library for building custom pages.

For the ERP, Frappe Desk gives us 90% of the UI for free. Use Frappe UI only for truly custom screens (e.g., a mobile technician app, a client portal page).

The three-tier classification in practice

OOTB  Use as-is

Feature exists in ERPNext/Frappe exactly as needed. Your job: configure and enable it. Enable the module, set permissions, configure workflows, write print formats.

Examples: Chart of Accounts, Purchase Order workflow, Leave policy, Stock valuation methods, GST tax templates.

No app code required. All config goes into fixtures.

Refine  Extend it

Feature exists but needs adjustment: extra fields, changed validation, additional child tables, UI tweaks, custom reports. Your job: add on top via Custom Fields, Property Setters, Server/Client Scripts.

Examples: Adding BANT fields to Lead DocType, adding a Dealer Scorecard child table to Customer, extending Sales Person targets with activity metrics.

Custom app required; fixtures for fields + scripts for logic.

Build  Create new

No Frappe equivalent, or the gap is too large to patch. Your job: build a new Custom DocType with its own controller, UI, and APIs inside your custom app.

Examples: AMC Management, Field Service Dispatch, Content Calendar, Fleet Management, Channel Partner Portal, Dealer Scorecard, Route Optimization engine.

Full Frappe app development: DocType + controller + client script + fixtures.

Known Frappe limitations — plan around these

LimitationImpact on AIWSMitigation
MariaDB only for app-layer data All ERP data in MariaDB. PostgreSQL not supported by Frappe ORM. Use PostgreSQL only for the separate control-plane service. ERP data stays in MariaDB — this is fine for ERP workloads.
Frappe Desk UI is functional but dated End-user experience may feel like a classic ERP (not a modern SaaS app) without customization. Use Frappe Workspaces + role-based dashboards to simplify the UX. Build truly custom pages (mobile apps, client portals) with Frappe UI (Vue.js) where needed.
Background jobs via Redis/RQ RQ is reliable for ERP-scale async work but is not Kafka-class message streaming. RQ is perfectly adequate for ERP event processing. The future Bridge will use a proper event backbone; the ERP just writes to an outbox table.
Performance ceiling under very high concurrent users Frappe is Python-based; at 500+ concurrent users per site, it needs careful tuning. Use Redis caching aggressively, set up Gunicorn workers correctly, and separate Tier B (dedicated) sites for large enterprise clients.
GPL licensing ERPNext is GPL v3. Frappe Framework is MIT. The GPL SaaS exception (AGPL does not apply here) means you can run GPL software as a service without open-sourcing your code. Legal review required before commercial launch (Open Question #8).
Frappe CRM is a separate app Frappe CRM (modern Vue-based) is distinct from ERPNext CRM (classic). They share the same DB but have different interfaces. Use Frappe CRM as the primary sales/pipeline UI. ERPNext Selling handles the transactional flow (Quotation → Order → Invoice). Both installed on the same site.

Bottom line: Frappe/ERPNext is a well-chosen foundation for this project. The ~70% OOTB coverage is excellent for a general-purpose ERP; the 30% gap is exactly the right kind of gap — feature-specific business logic that should be custom anyway. No red flags requiring a platform rethink.
